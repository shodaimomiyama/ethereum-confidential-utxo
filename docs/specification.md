# Confidential UTXOの仕様

## 目的と記載範囲

[PRD](PRD.md)と[要件定義](requirements.md)に基づき、方式に依存しない状態、操作、入出力の意味、受理と拒否、保証とその前提を定める。
暗号方式、方式固有の検証式、符号化、ABIなどの実現方法は設計で具体化する。
本書のモデル上で金額を扱うことは、その値を公開することを意味しない。

各節の「対応要件」は、要件定義の識別子で参照先を示す。
識別子の接頭辞は、FRが機能、SECが安全性、FVが形式証明、PRIVが機密性、EVALが評価、OPSが実行と再現性の要件を表す。

## 用語

[要件定義の用語](requirements.md#用語と関係者)を継承し、同一性や状態の判定に必要な意味を次のように具体化する。

| 用語 | 意味 |
| --- | --- |
| 所有者 | UTXOの使用を正当に認可できる論理的な主体。Ethereumトランザクションの送信者や、現実の人物の同一性とは区別する |
| 所有者識別情報 | UTXOがどの所有者に属するかを表す論理上の情報。具体的な鍵、アドレス、符号化との対応は設計で定める |
| 受取情報 | 送信者が受取人向けの出力を作るために事前共有する公開情報 |
| 受領データ | 受取人が金額を確認し、UTXOを再使用するために必要な情報。認可の秘密鍵とは区別する |
| チェーン上の操作の確定 | チェーン上で受理された操作が、採用する確定条件を満たした状態。受取人による受領成立とは区別する |
| 受領成立 | 確定したチェーン状態と受領データの整合性を確認し、本人が使用できるUTXOとして認識できた状態 |
| 未計上ETH | 正当な入金として認識されず、UTXOに対応する利用者への債務に計上していないETH。CLIが受領を認識できないUTXOの金額とは区別する |
| 論理操作 | 入金、送金、出金のいずれか一つの意図と、その資産状態の変化。Ethereumトランザクションとの対応方法は設計で定める |
| Auth（所有者認可） | 論理所有者が対象の論理操作を認可したことを確認する仕組み。特定の署名方式や外側のトランザクションの有効性とは区別する |
| Tx envelope | Ethereumトランザクションの送信形式と実行文脈。送信者、nonce、手数料、呼出し構成などを扱う |
| 提出者 | 認可済み操作を実行するため、外側のトランザクションを送信する主体。所有者、envelope上の送信者、呼出し元、ガス支払者との対応は経路ごとに定める |
| envelope上の送信者 | 採用するトランザクション形式で送信者として識別される主体。UTXOの所有者認可を自動的に与えるものではない |
| 呼出し元 | UTXOの操作を実行する境界で、その操作を直接呼び出す主体。中継や複数呼出しがあれば外側の送信者と異なり得る |
| ガス支払者 | 外側のトランザクションのgas費用を負担する主体。PoCでは公開ETHで支払う |
| 実行文脈 | 対象チェーンとデプロイ、適用する認可規則、呼出し元、当該操作の資金移動、現在の状態など、操作の受理を判断するための条件 |
| frame | 一つの呼出しなどの実行単位。失敗の影響が及ぶ範囲は経路ごとに確認し、外側のトランザクションとの同一性を仮定しない |
| 採用履歴 | 同期時に対象チェーンの履歴として採用する履歴。再編成で取り消された履歴は含まない |
| 利用可能残高 | CLIが受領成立、未使用、本人の使用権限を確認できたUTXOの合計。コントラクト全体の債務とは異なる |

## 論理状態と資産保存

対応要件: FR-01〜FR-04、SEC-01〜SEC-05、FV-01〜FV-03。

UTXOは識別情報、所有者、金額を持ち、生成後にそれらの意味を変更しない。
同一チェーンの同一デプロイの採用履歴上で、異なる生成に同じUTXO識別情報を割り当てない。
生成されたUTXOの状態は未使用または消費済みとし、一度消費したUTXOを同じ採用履歴内で未使用へ戻さない。
別のUTXOへの送金や再作成は、新たな生成と元のUTXOの消費として扱う。
再編成による履歴の取消と、採用履歴内での二重使用は区別する。

コントラクトストレージは、入力の存在、未使用、二重使用の拒否に必要な状態を保持する。
この論理モデルは、消費済みUTXOの全情報を永久にストレージへ残す方式を指定しない。
公開履歴からの受領と再同期に必要な情報は、ストレージ上の保持方法によらず取得可能とする。

本書の式では、`=`を等値、`+`を加算、`-`を減算または負符号、`×`を乗算に用いる。
`>`は左辺が右辺より大きいこと、`≥`は以上、`≤`は以下を表す。
関数名の後の丸括弧は関数へ渡す対象を表し、複数の対象はコンマで区切る。
状態を表す記号と、UTXOの情報を得る関数を次のように定める。

| 記号 | 意味 |
| --- | --- |
| `U` | 生成済みUTXOの論理的な記録の集合 |
| `u` | 一つのUTXOの論理的な記録 |
| `S` | 消費済みUTXOの識別情報の集合。`S`は`U`に存在する識別情報のみを含む |
| `id` | UTXOの記録から識別情報を得る関数。`id(u)`はUTXO `u`の識別情報 |
| `v` | UTXOの記録からwei単位の金額を得る関数。`v(u)`はUTXO `u`の金額 |
| `L` | 未使用UTXOの総額 |
| `B` | コントラクトが保有する実際のETH残高 |
| `E` | 未計上ETHの総額 |
| `H` | 採用履歴で成功した論理操作の集合。表現や提出経路が変わっても同じ操作を識別するための論理的な履歴 |

集合への所属を`∈`、所属しないことを`∉`、指定した条件に該当する要素についての総和を`Σ`で表す。
未使用UTXOは、生成済みの集合に属し、その識別情報が消費済みの集合に含まれないものなので、`L = Σ v(u)`（`u ∈ U`かつ`id(u) ∉ S`）となる。

初期状態はUTXOなし、`L = 0`、`H`は空とし、初期残高があれば`E = B`とする。
資産操作と、それに伴って受理した操作が完了した状態で、`B = L + E`かつ`E ≥ 0`を満たす。
`L`と`E`は仕様上の論理量であり、その値を公開したり、専用のストレージ変数を設けたりする要件ではない。
`H`も専用の保存領域や新たなnonce方式を指定せず、操作の識別と再使用の拒否に必要な論理上の意味を表す。
外部呼出しの途中の任意の観測点に同じ等式を要求するものでもないが、中間状態を悪用した無断使用や二重使用は認めない。

受領データを復号できない場合でも、未使用の生成済みUTXOは`L`に含める。
CLIの利用可能残高が減少したことだけを根拠に、`L`を減らしたり`E`へ振り替えたりしない。

### 収支への寄与

当該操作の入金額を`d`、公開出金額を`w`、未計上ETHとして受け取る額を`e`とし、いずれもwei単位で表す。
記号の前に付ける`Δ`は、当該操作またはETH受領の効果による増減への寄与を表す。
`ΔB`、`ΔL`、`ΔE`は、それぞれコントラクト残高、未使用UTXOの総額、未計上ETHの総額への寄与であり、正なら増加、負なら減少となる。

各操作の収支への寄与は、入金で`ΔB = ΔL = d`、送金で`ΔB = ΔL = 0`、出金で`ΔB = ΔL = -w`とする。
未計上ETHを受け取った場合の寄与は、`ΔB = ΔE = e`、`ΔL = 0`である。
受領先の処理で他の操作やETHの返送が起きる場合は、受理した効果をそれぞれ合成する。
合成前の値を`B`、`L`、`E`、対象となる効果をすべて合成した後の値を`B'`、`L'`、`E'`とし、末尾の`'`（プライム）で合成後を区別する。
例えば出金`w`に伴って未計上ETH `e`が戻り、別の正当な入金`d`も成立した場合、他の効果がなければ`B' = B - w + e + d`、`L' = L - w + d`、`E' = E + e`となる。
受領先の処理を無条件に無視して、出金額とコントラクト残高の純減を同一視しない。

### 未計上ETH

正当な入金操作を経ずにコントラクトへ届いたETHは、UTXOに対応する利用者への債務に計上しない。
コントラクトのETH残高が増えたことだけを根拠にUTXOを発行しない。

PoCには未計上ETHの返還や回収のための操作を設けない。
このETHはコントラクトの残高として残り、利用者や運営者の通常操作で引き出せる資産として扱わない。
出金で正当な債務を減らす場合も、未計上ETHを取り崩して出金額を増やすことは認めない。

## 金額と入出力数

対応要件: FR-01〜FR-04、SEC-01、PRIV-02〜PRIV-03。

金額はwei単位の整数とし、最小単位は1 weiとする。
操作の金額や収支計算では丸めを行わない。
方式に依存する上限値は、次の制約に従って設計で具体化する。

| パラメータ | 意味と制約 | 境界の振る舞い |
| --- | --- | --- |
| `M` | 単一UTXOの金額上限。整数で`M ≥ 10 wei` | 各UTXOは`1 ≤ v(u) ≤ M`。入金額も同じ範囲。上限ちょうどは許容し、上限超過は拒否 |
| `N` | 一つの送金または出金で消費できる入力数の上限。整数で`N ≥ 2` | `1 ≤ 入力数 ≤ N`。上限超過は部分実行せず拒否 |
| `W` | 公開出金額の上限。整数で`W ≥ M`。少なくとも各UTXOの全額出金を可能にする | `1 ≤ w ≤ W`かつ出金額は入力合計額以下。残額を生成する場合は残額も`M`以下 |

出力数は基本操作の表に従い、送金は1個または2個、出金は0個または1個、入金は1個とする。
入力合計と出力合計は数学的な整数で比較し、単一UTXOの上限とは区別する。
入出力の例では、`→`の左側に消費するUTXOの金額、右側に生成するUTXOの金額を並べ、同じ側の`+`で複数UTXOの合算を表す。
例えば`M + M → M + M`は、各入力と出力が範囲内であり、合計が`M`を超えることだけを理由に拒否しない。
全入力を使う操作で所定の出力数や金額範囲を満たせない場合は、その入力の組合せを拒否する。
整数のあふれ、負の値の読み替え、体の剰余を利用して、別の金額として保存条件を通過させられないようにする。
設計は`N × M`を含む必要な合計値を扱える表現と検証規則を定める。

入金、送金、出金の資産操作は正の金額を対象とし、0の金額を指定した資産操作を受理しない。
論理上の資産であるUTXOの金額も正の値とし、金額0のUTXOを生成しない。
全額使用して残額が0になる場合は、釣銭UTXOを生成しない。

方式の都合でダミー表現を使う場合、それを資産UTXO、使用可能な入力、利用可能残高、債務へ対応付けない。
ダミーは論理上の入出力数にも数えない。
採否、符号化、物理的なスロット数は設計で定め、ダミーを資産として使用できないことを検証する。

## 所有者と認可

対応要件: FR-03、SEC-02、SEC-04、FV-02〜FV-03。

### 所有者の同一性

同一所有者の合算は、同じ論理的な所有者に属する入力を対象とする。
各入力の認可を得られることと、各入力の所有者が同一であることは、それぞれ確認する条件である。

同じ人が複数の鍵を管理していることだけを根拠に、異なる所有者識別情報を同一所有者として扱わない。
以下の例では、異なる論理所有者を所有者A、所有者Bと呼び、文脈上明らかな場合はA、Bと略す。
所有者名のBは、コントラクト残高を表す数式中の`B`とは区別する。
例えば、一人の利用者が所有者Aと所有者Bに対応する鍵を両方保持していても、Aの入力とBの入力の合算は、必須の同一所有者の合算には含まれない。
現実の人物の身元を判定する条件は導入しない。

認可方式を変更しても、誰が当該UTXOの使用を認可できるかという意味と、同一所有者の判定を維持する。
新方式の鍵やアカウントを示すことだけで所有者を置き換えたり、使用権限を増やしたりしない。
運営者であることを理由とする使用権限は設けない。
以前の送信者が作成時に知った金額や受領情報も、受取人のUTXOを使用する認可に代わらない。
具体的な鍵、署名方式、アカウントと所有者の対応、およびその検証方法は設計で定める。

### 認可対象

認可は、対象チェーンとデプロイ、操作種別、入力、出力とその所有者、各金額、公開入出金額、公開出金先、受領データとの対応、同じ操作の再使用を識別する情報に結び付ける。
これらは論理上の認可対象であり、金額や非公開の受領情報を平文で公開する指定ではない。
具体的な表現、署名や証明、識別子、順序の符号化は設計で定める。
公開検証に渡す情報と実際の操作が同じ意味を持ち、認可対象の変更で別の意図を成立させられないことを要求する。

### 認可結果の検証

Authの検証と資産操作の実行を分ける場合、次の条件をすべて満たす。
これは論理上の条件であり、認可結果のデータ構造や公開形式を指定しない。

| 条件 | 必要な判定 |
| --- | --- |
| 真正性 | 誰が、どの規則で、どの所有者の認可を検証した結果かが確認でき、その主体と検証経路を信頼する根拠がある |
| 対象との結合 | 上記の認可対象と実行する論理操作が対応し、別操作への付替えや別環境への流用がない |
| 実行時の有効性 | 検証結果の適用条件が実行時にも成立し、現在の入力が未使用で、同じ論理操作が成功済みではない |

提出者が与えた成功フラグや所有者名だけでは、これらの条件を満たさない。
方式や版を識別する必要がある場合は、認可を解釈する規則とその適用範囲に識別を結び付け、未知の識別、不一致、異なる意味への読み替えを拒否する。
具体的な識別の配置や認可表現は設計で定める。
ある時点の検証成功だけでは、その後に入力が消費された操作や、適用条件が成立しなくなった操作の実行を認めない。
状態確認と消費・成功の確定の間に競合や再入があっても、各受理条件を保つ必要がある。

## 操作の範囲と状態遷移

対応要件: FR-01〜FR-04、SEC-01〜SEC-05。

### 基本操作

操作の入出力と金額には、次の記号を用いる。

| 記号 | 意味 |
| --- | --- |
| `I` | 当該操作で消費する入力UTXOの集合 |
| `O` | 当該操作で生成する出力UTXOの集合 |
| `i` | 入力集合`I`に属する一つのUTXOの記録 |
| `V` | 入力UTXOの金額の総和。wei単位 |
| `t` | 送金で受取人向けに生成するUTXOの金額。wei単位で、釣銭を含まない |

入力総額は`V = Σ v(i)`（`i ∈ I`）とする。
以下の数は論理上の資産UTXOの個数であり、物理的なスロット数ではない。

| 操作 | 入力と所有者 | 生成するUTXO | 公開ETHの移動 | 保存条件 |
| --- | --- | --- | --- | --- |
| 入金 | UTXO入力なし | 当該入金を認可した所有者のUTXOを1個 | 当該入金として実際に受け取る`d > 0` | 出力額`= d` |
| 送金 | 同一所有者の未使用UTXOを1個以上 | 受取人への`t > 0`を1個。`V - t > 0`なら入力所有者への釣銭を1個 | なし | `V = t + 釣銭額` |
| 出金 | 同一所有者の未使用UTXOを1個以上 | `V - w > 0`なら入力所有者への残額を1個 | 認可した一つの公開出金先へ`w > 0` | `V = w + 残額` |

入金では、実受領額、当該操作で認識する入金額、生成額を一致させる。
他の入金や未計上ETH、既存の裏付けETHを、その入金の支払いとして数えない。
入金で生成するUTXOの所有者にも、その入金操作への認可を要求する。
ETHを支払うEthereumアカウントと所有者の同一性は要求しない。
所有者の認可を得ずに、その所有者名義のUTXOを直接入金で作成する操作は拒否する。

一つの論理操作に公開入金と既存UTXOの消費を混在させない。
公開出金と第三者へのUTXO送金も、一つの論理操作には混在させない。
複数所有者の共同入力、複数受取人への出力、表にない入出力の組合せは、この仕様の論理操作として受理しない。
複数の独立した論理操作を一つのEthereumトランザクション内で扱うことまで禁止するものではない。
その実行経路と外部呼出しの構成は設計で定め、受理する各操作に本書の条件を適用する。

### 自己宛ての操作

送金の受取人は、入力の所有者と同一でもよい。
自己宛ての2入力から1出力への合算、1入力から2出力への分割、1入力から1出力への再作成を認める。
それぞれ通常の送金と同じ認可、金額範囲、資産保存、消費と生成の規則に従う。
自己宛てであることを理由に検証を省略せず、独立した操作種別も追加しない。

### 共通の受理条件

資産操作の受理には、次の条件をすべて満たすことを要求する。
条件を満たす操作は、必要な実行資源があり、外部受領が成功する場合に成立しなければならない。
外部呼出しからの再入については、失敗と外部呼出しの節で定める範囲で受理を制限できる。

1. 対象チェーン、デプロイ、操作種別、入出力数、データ項目が定義された範囲に入る。
2. 各入力は存在する未使用UTXOであり、同じ入力を一つの操作で重複させない。
3. 入力の所有者は同一であり、すべての入力の使用がその所有者によって認可されている。入金では生成先の所有者が操作を認可している。
4. 各出力の所有者と金額、入出金額が、操作ごとの条件と認可した意図に一致する。
5. 各金額と個数が範囲内であり、数学的な整数として保存式を満たす。
6. 新たに生成するUTXOの識別情報は互いに異なり、採用履歴上の既存UTXOと衝突しない。
7. 認可と検証が実行時に有効で、改ざんや別環境への流用に該当せず、同じ論理操作が`H`に存在しない。
8. 公開資産移動が必要な場合は、実受領または指定先へのETH移動が成功する。

入力のない入金には、入力に関する条件を適用しない。
暗号上の具体的な有効性条件は設計で定め、上記の条件を実際に保証することを検証する。
不正な証明や認可を受理したり、検証を省いたりして正常な操作と扱わない。

当該操作自体の効果として、`I`の全入力を消費済みにし、`O`の全出力を未使用として生成する。
成功した論理操作を`H`に加え、資産効果と一体に確定する。
当該操作自体は、対象外の既存UTXOの所有者、金額、使用状態を変更しない。
複数の操作や再入操作を受理する場合は、各操作の条件を満たす順序で効果を合成する。
例えば生成した出力を後の操作で正当に消費した場合、合成後の状態ではその出力は消費済みとなる。
資産移動、消費、生成、および公開される成功の記録は、対応する同じ操作を表す。

## トランザクションの提出と実行文脈

対応要件: FR-08〜FR-09、SEC-02、SEC-04。

| 責務 | 判定する内容 | 他の責務との関係 |
| --- | --- | --- |
| Tx envelope | 外側の送信形式、送信者、nonce、手数料、呼出し構成と実行条件 | 外側が有効であっても、UTXO所有者の認可や実入金の成立を意味しない |
| Auth | 論理所有者が、対象環境の当該操作を認可したこと | 検証結果の真正性、対象との結合、実行時の適用条件を保って状態遷移へ対応付ける |
| UTXO状態遷移 | 入力の存在・未使用・重複、所有者認可、範囲、資産保存、再使用、資産移動 | 条件を満たす場合だけ消費、生成、入出金と成功の記録を一体に確定する |

同一の処理や証明が複数の責務を果たしてもよい。
この区分は別コントラクトへの分割や、認可証明と金額証明を分けることを要求しない。

設計では、各経路の提出者、envelope上の送信者、直接の呼出し元、ガス支払者と論理所有者の対応を示す。
どの情報が外側の形式や実行基盤で検証され、どの情報を本体が検証するかを区別する。
例えば直接呼び出すPoC経路で提出者、外側の送信者、呼出し元、ガス支払者が一致しても、中継する経路の呼出し元へその一致を引き継がない。
呼出し元や外側の送信者だけを根拠に、UTXOの所有者、受取人、出金先を読み替えない。

実行文脈は、対象チェーンとデプロイ、適用する認可規則、検証された所有者と操作の対応、呼出し元、当該操作に対応する実入出金、実行時のUTXO状態と成功済み操作の履歴を含む。
経路が時点や版などの追加条件に認可を依存させる場合は、その条件も実行時の適用範囲として明示する。
採用経路で信頼できる文脈の由来を示し、提出者が任意に設定した値を検証済みの文脈として扱わない。

所有者が認可した入金、送金、出金は、異なるEthereumアカウントから同一の認可済み内容を提出できる。
提出者の相違だけを理由に拒否しない。
提出者に受取人や出金先を書き換える権限は与えない。

## 操作の再使用と競合

対応要件: SEC-03〜SEC-04、OPS-04。

| 範囲 | 守る条件 |
| --- | --- |
| 外側のトランザクション | 採用するenvelopeのnonceなど、送信と実行に関する条件を満たす |
| 論理操作 | 認可方式、提出経路、外側の取引、署名や証明の表現を変えても、同じ認可済み操作を二度成功させない |
| UTXO | 同じ入力の重複、競合、異なる操作からの使用でも、同じUTXOを二度消費しない |

外側のnonceを更新したことは、論理操作の新規性や入力の未使用性を保証しない。
成功済み操作の論理上の同一性は経路をまたいで保ち、方式別の識別表現だけを変えて`H`の未登録操作に見せられないようにする。
入力を持たない入金も対象とし、新たなETHを添えて経路を変えた同じ入金の再提出も拒否する。
別の操作として新たに認可した同額の入金は、その実受領があれば成立できる。
経路や署名表現を変えることだけを、新たな認可済み入金とみなさない。
具体的な操作識別、保存、nonceの有無と方式は設計で定める。

未確定操作の再提出と、成功済み操作の再使用を区別する。
入力が消費済みであることだけでは、意図した操作が成功したとは判断しない。
再試行時は、確定履歴の入力、出力、公開資産移動などを照合し、競合する別の認可済み操作と区別する。

## ガスと資産移動の会計

対応要件: FR-08、SEC-01。

PoCではgasを公開ETHで支払い、UTXOの保存式から差し引かない。
提出者とガス支払者の対応は採用する経路の条件として記録し、両者の一致をUTXO状態遷移の一般条件にしない。
gas不足や失敗取引の費用をUTXOから自動補填しない。

gas支出と返金は、UTXOの債務、裏付けETH、未計上ETH、正当な入出金と区別する。
ガス支払者へ戻る公開ETHを、UTXO所有者への出金や未使用UTXOの増加として計上しない。
UTXOコントラクト自身へETHが届いた場合は、その出所の名称によらず、認可された当該入金の実受領に対応するものだけを入金とする。
それ以外は未計上ETHとして扱う。
gas支払いのために裏付けや未計上ETHを取り崩したり、gasの支払い・返金が成立したことだけでUTXOを発行したりしない。

## 失敗と外部呼出し

対応要件: FR-04、FR-08、SEC-01、SEC-03、SEC-05。

### 確定と取消の単位

本体が一体に確定または取消する単位は、一つの論理操作の入力消費、出力生成、公開資産移動、成功済み操作としての記録である。
複数の呼出しやframeを通る経路でも、この単位の一部だけを確定しない。
出金先がETH受領を拒否した場合や、実行資源不足で操作を完了できない場合にも適用する。
失敗した操作を成功として示す履歴やCLI表示を残さず、`H`にも加えない。
外側のgas支出、返金、nonce更新の扱いは、この資産操作の取消から区別する。
設計ではどのframeの失敗がどの資産効果を取り消すかを示し、必要な失敗の伝播を保証できない経路を適合と扱わない。

### 出金先と再入

出金先には、所有者自身または第三者の通常アドレス、および当該ETHを受領できるコントラクトを指定できる。
受領先からの再入は、安全に拒否しても、認可された独立操作として受理してもよい。
いずれの場合も、無断使用、二重使用、資産生成、中間状態の悪用を認めない。
外側の操作が失敗した場合には、それに伴って受理した内側の操作の効果も取り消す。
内側の呼出しの失敗を受領先が処理したうえで正常にETHを受け取る場合まで、外側の出金失敗と決めつけない。

### 複数操作と外部接続

独立した複数の論理操作が同じ外側の取引に含まれることだけでは、その全体の原子性を保証しない。
[Uniswap接続の要求U-02](integration/uniswap/PRD.md#要求と成功の判断)では、出金と交換を一体に取り消す必要がある。
交換の失敗を処理して出金だけを残す経路は、外側の取引が成功してもU-02を満たさない。
接続側で必要な失敗伝播と取消範囲を具体化し、対応を検証する。
本体の一般の出金は、出金完了後に受領先が行う処理の成功まで保証しない。

## 受領の保証と不整合な受領データ

対応要件: FR-05〜FR-07、SEC-02、SEC-04、SEC-06、OPS-04。

受取人が正しい受取情報を事前共有し、必要な鍵を保持し、必要な公開履歴へアクセスできることを前提とする。
その受取情報から仕様に従う送信処理が生成した送金では、受取人がオフラインでも送金でき、確定後は送信者の追加協力なしで受領、金額確認、再送金、出金ができる。

送信者自身が不整合な受領データを作成して認可した場合、その不整合をすべてオンチェーンで拒否することまでは必須の保証に含めない。
この保証範囲は、資産保存、所有者の認可、操作意図との結合、不正な証明の拒否など、ほかの受理条件を緩和しない。
第三者が認可後に受領データなどの認可対象を改ざんして、別の操作を成立させることは認めない。

受取側は、復号不能なデータや、チェーン上のUTXOと整合しないデータを利用可能資産に計上しない。
チェーン上の操作が確定しても、それだけで受取人の受領成立とは扱わない。
受領を認識できないことだけを理由に、対応するUTXOを消費済みとしたり、その裏付けETHを未計上ETHへ振り替えたりしない。

説明例として、所有者Aが10 weiの入力から所有者Bへ3 wei、自分へ7 weiを生成する送金を考える。
正しく作成した送金では、BとAはそれぞれの出力を独立して使用できる。
A自身がB向けの受領データを誤って作成した場合、チェーン上の操作が確定していても、Bはその出力を受領済みの利用可能資産として扱わない。
この例は、送信処理の不具合を正常な動作として認めるものではない。
仕様に従う送信処理の正常経路で受領不能な出力が発生する場合は、FR-05〜FR-07への不適合として扱う。

## 外部インターフェースの意味

対応要件: FR-01〜FR-08、SEC-02〜SEC-06、OPS-03〜OPS-04。

ここではCLIとコントラクトが扱う情報の意味を定める。
コマンド名、関数名、引数の順序、ABI、イベント名、エラー番号は設計で具体化する。

| 操作・情報 | 入力の意味 | 結果の意味 |
| --- | --- | --- |
| 受取情報の提示 | 本人が保持する認可と受領の鍵に対応する公開情報 | 送信者が、その本人だけが正当に使用できる出力を作成できる情報 |
| 入金要求 | 所有者、公開入金額、生成する出力、受領データとの対応、所有者の認可、必要な検証情報 | 実受領額と一致する自身のUTXOが1個生成された操作 |
| 送金要求 | 消費する入力、受取情報、送金額、釣銭、生成する出力、受領データとの対応、所有者の認可、必要な検証情報 | 全入力が消費され、受取人と必要なら自身への出力が生成された操作 |
| 出金要求 | 消費する入力、公開出金先、出金額、残額、必要な受領データとの対応、所有者の認可、必要な検証情報 | 全入力が消費され、指定先へのETH移動と必要な残額の生成が完了した操作 |
| 操作履歴 | 対象チェーンとデプロイ、操作を特定する情報、履歴の範囲 | 操作種別、消費と生成の対応、公開入出金、受領の発見と整合性確認に必要な公開データ、履歴の位置と確定状況 |
| UTXOの状態確認 | 対象環境とUTXO識別情報 | 存在と未使用または消費済みの状態。照合したチェーン状態も特定可能とする |
| CLI同期 | 本人の鍵、対象環境、取得対象の履歴 | 本人の受領、使用済み状態、利用可能残高、未確定や確認不能の区別 |

公開インターフェースに渡す金額や受領情報の表現は、機密性の規則に従う。
本人のCLIが作成に用いる秘密情報を、そのまま公開要求へ含めるものではない。
拒否では、不正な形式、範囲外、入力の不存在・重複・消費済み、認可や検証の不成立、外部受領の失敗などの理由を、観測できる範囲で識別する。
暗号方式の構成によって細かな理由を公開判定できない場合は、検証の不成立として扱える。
複数の拒否条件を満たす入力について、エラーの優先順位は固定しない。
通信失敗や未取得の結果を、コントラクトが拒否した結果に置き換えない。

## 受領と同期の状態

対応要件: FR-05〜FR-07、SEC-03、SEC-06、OPS-04。

チェーン上の受理、確定条件の充足、受領データの確認、UTXOの使用状態を別々に確認する。
確定条件は、対象ネットワークで履歴を確定と扱うための条件である。
ネットワークごとの設定値と根拠は設計と実行手順に固定し、CLIは適用した条件と照合した履歴の位置を示す。
受領データの存在や復号の成功だけを、チェーン上の成功や受領成立の証拠にしない。

| 状態 | 判定 | CLIと再試行の扱い |
| --- | --- | --- |
| 未確定 | 提出済みまたは採用履歴に含まれたが、確定条件を満たさない | 成功と断定せず、出力を利用可能残高へ加算しない |
| 確定した成功 | 採用履歴で操作の成功と確定条件を確認できる | チェーン上の成功を示す。受領成立は別途確認する |
| 確定した試行の失敗 | 対象の実行試行の失敗を確定履歴から確認できる。トランザクション全体の失敗、または成功したトランザクション内での当該操作の失敗を含む | 当該試行の失敗を示す。同じ論理操作が別の試行で成功していないかは別途照合する |
| 受領成立・未使用 | 確定した出力と受領データが整合し、本人の使用権限と未使用を確認できる | 当該UTXOを一度だけ利用可能残高へ計上する |
| 消費済み | 照合した採用履歴で消費済みと確認できる | 利用可能残高に含めない。どの操作による消費かを照合できるようにする |
| 復号不能・不整合 | 復号できない、または出力の所有者・金額などと整合しない | 利用可能残高に含めない。チェーン上のUTXOを削除したり、消費済みとみなしたりしない |
| 確認不能 | 必要な履歴や状態を取得できず、現時点の結果を判定できない | 成功、失敗、未実行のいずれとも断定しない。以前の確認結果を示す場合は、その時点と未更新であることを区別する |

Ethereumトランザクション全体の成功だけで、その内部の対象操作も成功したと判断しない。
公開履歴から対象操作の成功または失敗の根拠を確認できない場合は、確認不能として扱う。

再同期は、同じ環境と同じ採用履歴から同じUTXOの状態と金額を復元できるものとする。
同じ履歴を繰り返し取得しても同一UTXOを重複計上しない。
既存のローカル残高へ単純に加算せず、生成と消費を対応付けて照合する。
再編成を検出した場合は、取り消された履歴に基づく生成、消費、確定判定を見直し、採用履歴から再計算する。
取り消された生成を利用可能資産として残さず、取り消された消費も新しい採用履歴と照合する。

確認不能の間に、未実行と仮定して同じ資産を再使用したり、出力を利用可能と扱ったりしない。
再試行前に、対象操作の確定状況と入力の最新の使用状態を照合する。
競合する操作で入力が消費されていた場合は、意図した操作の成功と扱わない。
履歴へのアクセスが回復した後は、鍵と公開履歴だけで同期を再実行できる。

## 公開情報と秘密の範囲

対応要件: SEC-06、PRIV-01〜PRIV-03。

| 情報 | 公開と保持の規則 |
| --- | --- |
| 消費と生成の関係 | 公開する。入力と出力の対応、操作の入出力数、後続の使用を観測可能とする |
| 入出金 | 入出金額と公開出金先は公開される |
| 所有者情報 | 所有者識別情報とその同一性、送信者・受取人・釣銭の区別の秘匿は保証しない。具体的な公開形式と、そこから分かる関係を設計で列挙する |
| 機密送金の金額 | 金額の平文を公開データへ含めない。本人への表示と、入出金や既知情報による推論は区別する |
| 認可と受領の秘密鍵 | 当該利用者が保持する。オンチェーン、共有成果物、通常の診断ログへ平文で出さない |
| 作成時の受領情報 | 作成者は作成に必要な情報を知り得る。その情報だけでは受取人の使用を認可できないものとする |
| 公開される受領データ | 保持する鍵と公開履歴から、本人が発見、復号、整合性確認できる情報を提供する。平文漏えいを認めない |
| その他のメタデータ | Ethereumの送信元、履歴の位置、時刻に関する情報、gas、データ量、証明や受領データの形など、実装で観測可能な情報を評価に含める |

可逆な符号化だけでは金額の秘匿を満たさない。
採用する方式の安全性の根拠と前提、および公開情報全体から金額が推論される条件を説明する。
所有者情報の公開を許容することは、実際に公開する情報を省略して評価してよいという意味ではない。
研究用の既知値や試験鍵を意図的に公開する場合は、公開の目的と範囲を明示し、通常利用の秘密と区別する。

### 推論シナリオ

以下では金額をwei単位とし、観測者が知るすべての資産移動を列挙する。
gasをUTXOの金額から差し引かない。
部分送金で生成する二つのUTXOの金額を、それぞれ`a`、`b`とする。
これらは正の整数であり、UTXO自体の識別情報や所有者名ではない。

| ケース | 観測情報 | 収支から得られる結果 |
| --- | --- | --- |
| 全額送金 | 公開入金により入力10が既知。出力は1個で他の資産移動なし | 出力は10と一意に決まる |
| 部分送金 | 入力10から金額`a`、`b`の2出力。他の資産移動なし | `a + b = 10`。収支だけでは`a`は1〜9、`b = 10 - a` |
| 相手の既知額を追加 | 同じ部分送金について`a = 3`を知る | `a = 3, b = 7`に絞られる |
| 後続出金 | 金額`a`のUTXOだけを入力として残額なしで3を公開出金したと分かる | 過去の`a = 3, b = 7`が分かる |

1〜9という範囲は収支制約だけによる候補であり、一つの暗号的な金額表現に複数の正しい開示値があることを意味しない。
実際の評価では、所有者情報、データ量、gasなどの追加制約を適用し、残る候補と暗号的な秘匿の根拠を区別して示す。
後から公開履歴が消えるとは仮定せず、追加情報の取得前後で同じ対象金額を比較する。
全ケースの厳密な候補数計算は必須にしないが、公開情報全体を踏まえて複数候補が残る実例はPoCで示す。

## 経路間の資産効果の同等性

対応要件: FR-09、FV-01〜FV-04。

次の二つは責務の違いを比較する抽象経路であり、特定のNative AA提案や実装構成を表さない。
PoCで二つとも実装する要件ではない。

| 経路 | 共通の状態遷移へ進むまでの条件 |
| --- | --- |
| 経路P | 資産操作の実行経路内で所有者認可を検証し、現在の受理条件を確認する |
| 経路Q | 先行する段階の認可検証結果を受け取り、真正性、対象との結合、実行時の適用条件と現在の受理条件を確認する |

比較に使う操作、状態、条件と関数を次のように定める。
関数は論理上の対応を表し、実装の関数名やABIを指定しない。

| 記号 | 意味 |
| --- | --- |
| `q` | 両経路で比較する、同じ認可済みの論理操作 |
| `rP`、`rQ` | それぞれ経路P、経路Qへ渡す要求 |
| `decodeP`、`decodeQ` | それぞれの経路の要求を、共通の論理操作へ対応付ける関数 |
| `σ`（シグマ） | 操作を実行する直前の論理状態。生成済みUTXO、消費済み識別情報、残高、未計上ETH、成功済み操作の履歴を含む |
| `c` | 比較する実行に適用する資金移動条件。当該入出金の成立条件を含む |
| `execP`、`execQ` | それぞれ経路P、経路Qでの実行を表す関数。事前状態、当該経路の要求、資金移動条件をこの順に受け取り、実行結果を返す |
| `T` | 共通モデルの状態遷移を表す関数。事前状態、論理操作、資金移動条件をこの順に受け取り、論理上の資産効果と操作後の状態を返す |
| `π`（パイ） | 各経路の実行結果から、比較対象となる論理上の資産効果と操作後の状態を取り出す関数 |

`σ`は、先行する認可検証時の古い状態で代替しない。
外部呼出しの返送ETHや受理した再入操作まで合成した結果を比較する場合は、それらの効果と順序も`c`に含め、両経路で同じ条件にそろえる。

`π`が取り出す比較対象は、消費と生成、所有者と金額、UTXOの債務、裏付けETHと未計上ETH、認可した公開入出金、成功済み操作の論理上の記録である。
`≅`は、識別情報の表現差を一意な対応で吸収したうえで、これらの意味と履歴への対応が同じであることを表す。
異なる生成や操作を同じものに潰したり、同じ成功済み操作を別の新規操作へ読み替えたりする対応は認めない。
外側の取引ハッシュ、nonce、gas、署名や証明のバイト列の一致は比較しない。

`decodeP(rP) = decodeQ(rQ) = q`となる要求を比較する。
同じ事前状態`σ`と資金移動条件`c`に対し、双方の外側の条件、認可、必要な実行資源が有効なら、各経路は同じ共通遷移`T`へ対応しなければならない。

```text
π(execP(σ, rP, c)) ≅ π(execQ(σ, rQ, c)) ≅ T(σ, q, c)
```

この式を、各経路から共通モデルへの適合条件とする。

例えば出金が両経路で成功しても、一方だけで受領先が1 weiを返すなら、最終的な`E`は異なり得る。
外部効果が異なる場合は、当該出金自体の寄与`ΔB = ΔL = -w`など、同じ条件を満たす部分について比較する。

比較対象の具体例は、[必須の動作シナリオ](#必須の動作シナリオ)に従う。
動作シナリオの識別子は、接頭辞Sと連番をハイフンで結んで表す。
S-01、S-03、S-06に同じ事前状態と資金移動条件を適用すると、両経路の消費、生成と収支は基本操作の表から同じ結果となる。
認可の不成立、再使用、実入金不足、実行時の競合、受領先の失敗については、S-01、S-09〜S-11、S-17〜S-18の拒否条件を両経路に適用する。
拒否の対象は当該論理操作とし、独立した操作や外側の費用の扱いは、失敗と外部呼出しの規則に従う。

この同等性は資産効果についての条件であり、公開情報、機密性、費用の同等性を意味しない。
採用する実経路の認可や受領データ、所有者情報、gasなどを、PRIVとEVALの要件に従って評価する。

## 必須の動作シナリオ

各正常例は、認可、公開履歴へのアクセス、必要な鍵と公開ETH、実行資源、外部受領の成功を前提とする。
各行は実装が満たすべき期待結果を示す。

| ID | 入力・操作 | 期待結果 |
| --- | --- | --- |
| S-01 | 所有者Aが認可した10の入金 | 実受領10と一致するAのUTXOを生成し、Aが後続使用できる。無認可、実受領との差異、0、範囲外は拒否 |
| S-02 | Aの10をBへ全額送金 | Aの入力を消費し、Bの10を1個生成。0の釣銭を生成しない |
| S-03 | Aの10からBへ3を送金 | Bの3とAの7を生成し、各所有者が独立して使用できる |
| S-04 | Aの2と3を合算しBへ4を送金 | 両入力を消費し、Bの4とAの1を生成。入力の重複、消費済み、不存在、別所有者の混入は全体を拒否 |
| S-05 | 自己宛てに2と3を5へ合算、10を3と7へ分割、10を10へ再作成 | 通常の送金規則に従って成立し、新旧UTXOを区別する |
| S-06 | Aの10から10または3を出金 | 自分、第三者の通常アドレス、ETH受領可能コントラクトの各宛先で成立。全額なら出力なし、部分ならAの7を生成して再使用可能 |
| S-07 | Bを停止して送金を確定し、その後Aも停止 | Bが鍵と公開履歴だけで同期、金額確認、再送金、出金できる。両使用のために複数の受領または部分使用の残額を用意する |
| S-08 | 復号不能、不整合、未確定の受領、同じ履歴の再取得 | 利用可能への誤計上、同一UTXOの二重計上をしない。正常なCLIが不整合データを生成した場合は不適合 |
| S-09 | 他者の無認可使用、以前の送信者による使用、認可結果の偽装や付替え、意図の改ざん、別環境への流用、方式や版の誤解釈 | 対象操作を拒否し、資産状態を変更しない。受領情報を知ることを認可とみなさない |
| S-10 | 同じ入力を使う競合操作と成功済み操作の再使用 | 採用履歴上で入力を一度だけ消費。経路Pで成功した操作をQから再提出しても拒否し、逆方向も同じ。同じ意図のコピー提出と異なる意図による消費を区別 |
| S-11 | ETH受領先の失敗、再入、操作中の実行失敗 | 部分確定なし。受理した内側の操作も外側の失敗時に取消。安全な再入拒否または受理が成立 |
| S-12 | 正当な入金以外でETHを受領 | `E`だけを増やし、UTXOを発行しない。出金先からの返送も同じ分類規則を適用 |
| S-13 | `1`、`M`、`M + 1`、負の値を装う表現、演算境界、入力数`N`と`N + 1` | 定めた境界で受理または拒否。`M + M → M + M`を単一UTXO上限の誤適用で拒否せず、剰余やあふれによる資産生成を拒否 |
| S-14 | 所有者とは別のアカウントが認可済み内容を提出 | 認可した効果のみ成立。採用するPoC経路のガス支払者の公開ETHからgasを支払い、UTXOや出金先を変更しない |
| S-15 | RPC通信失敗、未確定、再編成、失敗後の再試行 | 確認不能を未実行とみなさず、採用履歴に従って再同期し、成功済み操作を再使用しない |
| S-16 | 公開データ、通常ログ、共有成果物の確認 | 非公開の秘密を平文で含めず、本人向け表示と研究用に公開する既知値を区別 |
| S-17 | 経路Pで成功した認可済み入金を、新たなETHを添えて経路Qで再提出。その後、同額を別の操作として新たに認可して入金 | 最初の再提出は拒否し、追加の発行をしない。別途認可した新しい入金は、実受領に対応して成立 |
| S-18 | 認可の検証後、実行前に別操作が入力を消費するか、認可の適用条件が失効 | 先行する検証が成功していても、当該操作を拒否し資産効果を残さない。成功した競合操作の効果は維持 |

## 証明義務と検証の境界

対応要件: FR-09、FV-01〜FV-04。

| 命題・対応 | 検証すべき内容 |
| --- | --- |
| 状態モデルの資産保存 | 初期状態から受理する遷移で`B = L + E`を保ち、正当な入金以外から債務を発行しない |
| 状態モデルの認可 | 入金先の認可と、消費する各入力の所有者の認可が操作意図に対応し、別環境への流用を認めない |
| 状態モデルの一度だけの消費 | 存在する未使用入力だけを一度消費し、重複・競合・再使用による二重使用を防ぐ |
| 成功済み操作の再使用防止 | 入力を持たない入金を含め、同じ認可済み操作の二度目の成立を拒否する。別途認可した同額の新しい操作は区別する |
| 状態モデルの失敗 | 外部呼出しと再入を含め、失敗した操作に部分確定を残さない |
| 正常操作の成立 | 前提を満たす入金、全額・部分送金、合算、自己宛て操作、全額・部分出金が成立する。すべて拒否するモデルで代替しない |
| 本体実コードとモデル | 資産管理、認可、入力検証、消費と生成、外部呼出し、失敗処理がモデルに適合する |
| 検証入力と結果の利用 | 実際の操作を表す入力を検証器へ渡し、その結果に従って受理または拒否する |
| 暗号検証器と詳細規則 | 検証器の実コードが、設計で具体化する暗号上の検証規則どおりに判定する |
| 回路または検証関係とモデル | 本体固有の回路や検証関係が、本書の金額範囲、保存、認可など必要な条件を表す |
| 採用経路と共通の論理操作 | 認可と提出経路から共通モデルへの対応を保つ。認可検証結果の真正性、認可対象と実行対象の結合、実行時の有効性、経路をまたぐ再使用の拒否、原子性の範囲を含む |

これらの機械検証はPoC全体の必須成果とし、仕様策定での説明や確認だけでは充足しない。
手作業の対応表、モック、テストの成功だけを、実コードの形式証明へ置き換えない。
暗号方式自体の安全性の根拠と仮定は示すが、その暗号学的安全性の形式証明は初期必須にしない。
検証器全体の正しさや、本体固有の検証関係の適合を未証明の前提として省略しない。

要件ID、命題、対象モデル、実コードとコミット、具体的な検証規則、ツールと依存版、設定、信頼前提、公理、実行手順、成否を追跡可能にする。
EVM、コンパイラ、プリミティブなどの信頼境界と未証明箇所を列挙する。
証明穴、検証の無効化、未実行、スキップ、タイムアウト、未判定を合格と扱わない。
CLI、証明生成、配送のプログラムは自動テストと第三者による再現を対象とし、本体固有の検証関係の証明対象と区別する。
認可を別の段階や抽象的な述語として表しても、採用した実経路の検証主体と受け渡す結果が認可条件を満たすことを、実コードで機械検証する。
抽象経路の比較や認可述語の仮定だけでは、実コードの適合や別方式への移行を検証したことにならない。
