# Confidential UTXOの要件定義

## 目的

Ethereumの共通システムコントラクトとしての利用を目指すConfidential UTXOについて、研究プロトタイプ（PoC）に必要な機能、安全性、機密性、評価の受入条件を定義する。
対象は[Confidential UTXOのPRD](PRD.md)のP-01〜P-05とする。

## 対象範囲と共通前提

| 区分 | 条件 |
| --- | --- |
| 必須の対象 | ETH専用で実資金を扱わない研究プロトタイプ。操作と検証にはCLIと再現可能なスクリプトを使用 |
| 実行基盤 | PoCはEthereum上の通常のコントラクトとしてデプロイ。UTXOの状態をコントラクトストレージに保持 |
| 公開情報 | UTXOの消費と生成の関係を公開。入出金額と取引情報も観測者が利用できる前提 |
| 秘匿対象 | 機密送金の金額。公開情報から推論される限界も評価する |
| 鍵と権限 | 利用者が自分の鍵を管理。運営者が他人の資産を動かす特権を持たない |
| 実行環境 | ローカルと少なくとも1つのEthereum公開テストネットの両方 |
| 外部依存 | チェーンの動作、必要な履歴を取得できる通常のノードやRPC、利用者が保持する鍵、ガス用の公開ETH |
| 任意の補助 | 手動の受領データのエクスポートやインポート。通常受領の必須経路にはしない |
| 初期必須の対象外 | GUI、ERC-20、取引グラフの秘匿、所有者アドレスや公開鍵の秘匿、複数人への一括送金、複数所有者の共同入力、ガス肩代わり、外部監査、網羅的な先行方式比較 |
| 保証の対象外 | 本番運用、実資金の安全な運用、鍵紛失時の資金救済、本番SLA、障害復旧サービス、通信経路監視や端末侵入への対策 |

ローカルでは自動テストと比較評価、公開テストネットでは本体の動作とgasを検証する。
必要な証拠はOPS-01とOPS-02で定める。

所有者情報の公開形式は仕様で定め、金額推論に与える影響を評価する。
暗号方式、数式、API、格納形式、ツール、測定条件は、各要件の受入条件を満たすように仕様と設計で定める。

## 用語と関係者

| 用語 | 意味 |
| --- | --- |
| UTXO | 金額と使用権限に関する情報を持つ出力。未使用か消費済みかを管理し、消費と生成によって資産を移転する |
| 所有者 | 対象UTXOの使用を正当に認可できる利用者。Ethereumトランザクションの送信者とは概念上区別する |
| 受取情報 | 受取人向けの出力を作るために事前共有する公開情報。秘密鍵や各送金の受領データとは異なる |
| 受領データ | 受取人が金額を確認し、UTXOを再利用するために必要な情報。配送形式は未選定 |
| 受領の確認 | 確定したチェーン状態と受領データの整合性を確認し、本人が利用できるUTXOとして認識すること |
| 形式証明 | 命題を機械検証すること。状態モデルの性質と実装の適合の両方を含む |
| 第三者による再現と検証 | 公開されたコード、入力、環境設定、手順を使い、開発者以外の人が操作や測定を再実行して結果を確認すること |
| 収支推論の候補 | 観測者が知る収支条件などと整合する金額の候補。単一コミットメントに複数の正しい開示値があるという意味ではない |

| 関係者 | 知る情報 | 保持する秘密 | 公開する情報 | 認可できる操作 |
| --- | --- | --- | --- | --- |
| 送信者 | 自分の入力、送金額、釣銭、受取情報、作成に必要な受領データ | 自分の認可鍵など、仕様で必要とする秘密 | トランザクションと出力に必要な公開情報 | 自分のUTXOの送金と出金。作成時に知った情報だけで受取人のUTXOを使用できない |
| 受取人 | 自分宛ての受領データ、受領額、自分の使用可能UTXO | 自分の認可と受領に必要な鍵 | 事前の公開受取情報、再利用時のトランザクション | 受領確認後、自分のUTXOを送信者の追加協力なしで使用 |
| 公開情報のみの観測者 | チェーン履歴、公開グラフ、入出金額、所有者に関する公開情報、gasなど | 利用者の秘密を持たない | 観測に公開操作は不要 | 他人のUTXOを認可できない |
| 取引相手の情報も知る観測者 | 公開情報に加え、相手が知る金額など、評価で指定した追加情報 | 評価で明示する追加情報のみ。認可鍵の侵害は保証範囲外 | 追加の公開は必須でない | 金額等を知るだけでは他人のUTXOを認可できない |
| 検証を再実行する開発者や研究者 | 仕様、コード、測定条件、生データ、公開した試験入力 | 自分の検証用鍵。実利用者の鍵は不要 | 再現に必要なコード、手順、検証結果 | 自分の試験資産を操作 |
| デプロイや環境を管理する運営者 | 運用に必要な公開設定と履歴 | 他人の資産を使用できる秘密を必須にしない | 対象コード、環境とデプロイの情報 | 運営者であることによる他人の資産の使用権限は持たない |

## 機能要件

例の10、3、7、2、4、1は同じ資産単位の値とする。
具体的な金額単位、範囲、符号化は、これらのシナリオを満たす形で仕様化する。
各要件の正常系と異常系を、実際の暗号検証を使って確認する。

### FR-01 ETHの入金

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」、P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 入金する利用者。
- **前提**: 利用者が公開ETHと自分の使用権限に必要な鍵を持ち、入金処理に必要なガスを支払える。
- **要件**: 利用者が公開ETHを入金して、自分が正当に使用できるUTXOを生成できる。実際の入金額と生成するUTXOの金額が整合する。
- **受入条件**: 正常: 公開ETHを入金すると、実受領額と一致する自分のUTXOを確認して使用できる。異常: 実受領額を超える発行、無効な入力、資金不足ではUTXOの一部だけを生成しない。
- **検証方法**: 実際の暗号検証を使う入金と後続使用の自動テスト、公開テストネットでの取引記録。資産保存と失敗処理はSEC-01、SEC-05、FV-01〜FV-03で確認する。
- **限界と依存**: 入金額は公開される。入金の認識規則と金額表現は仕様で定める。

### FR-02 全額送金と部分送金

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」。
- **区分**: 必須。
- **対象者**: UTXOの所有者である送信者と受取人。
- **前提**: 送信者が未使用UTXOと認可に必要な鍵を持ち、受取人の公開受取情報を取得している。
- **要件**: 他者への全額送金と部分送金ができる。部分送金では受取人への出力と自分への釣銭を扱う。例：10から3を送り、7を自分に残す。
- **受入条件**: 正常: 全額送金と、10のUTXOから受取人へ3、送信者の釣銭へ7を生成する部分送金が成立し、両者が各出力を使用できる。異常: 所有者の認可がない送金や入力額を超える出力を拒否し、入力を消費しない。
- **検証方法**: CLIによる送金から受取人と送信者それぞれの再使用までの自動テスト。認可と資産保存の形式証明。
- **限界と依存**: 受取人1人と自分への釣銭を最低範囲とする。複数人への一括送金は初期必須ではない。

### FR-03 同一所有者のUTXOの合算

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」。
- **区分**: 必須。
- **対象者**: 複数の未使用UTXOを持つ所有者。
- **前提**: 各入力UTXOの所有者が同じであり、所有者がすべての入力を認可できる。
- **要件**: 同じ所有者の複数UTXOを合算して使用できる。例：2と3を合わせて4を送り、1を残す。少なくともこの操作を満たす入出力数を扱う。複数所有者による共同入力や複数受取人への一括送金は初期必須にしない。
- **受入条件**: 正常: 2と3のUTXOを同時に使用して他者へ4を送り、自分に1を残せる。両入力は消費済みとなり、2つの出力を正当に使用できる。異常: 同じ入力の重複、消費済み入力、他人の無認可入力を混ぜた操作を拒否し、一部の入力だけを消費しない。
- **検証方法**: 2入力から受取人と釣銭への送金、および不正な組合せの自動テスト。消費と生成の形式証明。
- **限界と依存**: 必要なシナリオを満たす入出力数の上限は仕様で決める。複数所有者による共同入力は初期必須ではない。

### FR-04 全額出金と部分出金

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」、P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 出金する所有者と、所有者が指定するETH受領先。
- **前提**: 所有者が未使用UTXOを認可でき、指定した受領先が当該ETHを受け取れる。
- **要件**: 全額出金と部分出金ができる。所有者が指定する自分や第三者の通常アドレス、およびETHを受領できるコントラクトを出金先にできる。部分出金では残額を正当に使える状態に保つ。
- **受入条件**: 正常: 自分、第三者の通常アドレス、ETH受領可能コントラクトの各出金先で全額出金と部分出金が成立する。部分出金の残額は所有者が再使用できる。異常: 出金先や金額の改ざん、過剰出金、受取先の失敗では資産移動とUTXO更新の一部だけを確定しない。
- **検証方法**: 各出金先への全額と部分出金、受取先が失敗するケース、再入を試みるケースの自動テスト。外部呼出しを含む形式証明。
- **限界と依存**: 公開出金額と出金先は公開される。出金完了後に受領コントラクトが行う処理は保証範囲に含めない。

### FR-05 受取人の同時応答を必要としない受領

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」、P-04「第三者が実装と評価を再現して検証できる」。
- **区分**: 必須。
- **対象者**: 送信者と、送金時にオフラインの受取人。
- **前提**: 受取人が自分の鍵を保持し、公開受取情報を事前共有している。同期時には通常のノードやRPCから必要な公開履歴を取得できる。
- **要件**: 受取情報の事前共有後、受取人がオフラインでも送信者が送金を確定できる。確定後に送信者が停止しても、受取人は保持する鍵と公開チェーン情報からCLIで同期し、受領の発見、金額確認、再送金、出金ができる。
- **受入条件**: 正常: 受取側プロセスを停止した状態で送信者が送金を確定し、その後送信側プロセスも停止する。受取人はCLIの同期だけで受領を発見し、金額を確認し、再送金と出金を行える。異常: 同時応答や送信者の追加協力を要求する場合は不合格とする。
- **検証方法**: プロセス停止を組み込んだ一連の操作の自動テストと、第三者による再現と検証。再送金用と出金用の受領を用意するか、部分使用の残額で両操作を確認する。
- **限界と依存**: 事前の公開受取情報の共有は許容する。鍵紛失、必要な履歴を取得できない環境からの復旧は保証しない。

### FR-06 公開チェーンからの受領データ取得

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」、P-04「第三者が実装と評価を再現して検証できる」。
- **区分**: 必須。
- **対象者**: 受領を同期する利用者とCLIの実装者。
- **前提**: 受取人の鍵が保持され、必要な履歴を通常のノードやRPCから取得できる。
- **要件**: 正常な送金ごとにファイル、秘密情報、受領データを人手で渡すことを要求しない。必要な履歴を通常のノードやRPCから取得できる前提で、専用配送サーバーに依存しない。手動のエクスポートやインポートは任意の補助手段とする。
- **受入条件**: 正常: 各送金について人手の配送をせず、専用配送サーバーを用いなくても、鍵と公開チェーン情報から受領に必要なデータを取得できる。異常: ファイル受渡し、送信者からの秘密情報の再送、専用配送サービスがなければ通常受領が成立しない構成は不合格とする。
- **検証方法**: 手動インポートと専用配送サービスを使わずFR-05のシナリオを再実行して結果を確認する。使用したRPCと履歴取得の条件を記録する。
- **限界と依存**: 手動エクスポートやインポートは任意の補助手段とする。データの格納形式、暗号化方式、検索方法は設計で選定する。

### FR-07 受領の整合性確認と残高認識

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」、P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 受取人とCLIの実装者。
- **前提**: CLIが保持する鍵と公開チェーンから取得した状態および受領データを照合できる。
- **要件**: CLIが受領データとチェーン上のUTXOの整合性を確認し、利用可能なUTXOとその金額を確認できる。復号できないデータや不整合なデータを受領済み資産として計上しない。再同期で同一受領を二重計上しない。
- **受入条件**: 正常: 復号した受領データが確定したUTXOと整合し、自分が使用できる場合に、そのUTXOと金額を表示する。異常: 復号不能、内容不整合、未確定の受領を利用可能資産へ加算しない。同じ履歴を再同期しても同一受領を二重計上しない。
- **検証方法**: 正常受領、復号不能、改ざんデータ、繰り返し同期を扱うCLI自動テスト。消費後の利用可能状態もチェーンと照合する。
- **限界と依存**: 表示する確定条件と再同期の振る舞いはOPS-04に従い仕様化する。金額を本人に表示することは公開漏えいと区別する。

### FR-08 公開ETHによるガス代支払い

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」、P-02「利用に必要なコストを先行方式と比較評価できる」。
- **区分**: 必須。
- **対象者**: 入金、送金、出金を実行する利用者と評価者。
- **前提**: 操作する利用者がUTXOとは別にガス支払い用の公開ETHを持つ。
- **要件**: 入金、送金、出金のガス代は、操作する利用者が別途持つ公開ETHで支払う。UTXO内の資産額とガス代を区別して収支を検証する。UTXOからのガス代支払い、ガス代の肩代わり、専用の送信代行サービスは初期必須にしない。
- **受入条件**: 正常: 各操作でUTXOの資産収支と公開ETHから支払うガス代を区別して確認できる。異常: 公開ETHのガス不足や失敗取引をUTXOからの自動補填で成功扱いしない。失敗時のガス代を資産保存違反や返還済みの額に誤計上しない。
- **検証方法**: 取引前後の公開残高、入出金額、UTXO状態、取引receiptのgasを分けて記録する自動テストと測定。
- **限界と依存**: UTXOからのガス支払い、肩代わり、専用送信代行は初期必須ではない。所有者の認可とEthereumトランザクションの送信者という概念は区別する。

## 安全性要件

実際の暗号検証を必須とし、検証の省略やモックの成功で適合を主張しない。
自動テスト、形式証明、暗号方式自体の安全性の根拠は、それぞれ異なる証拠として扱う。
テストの成功だけで暗号学的安全性を証明したとしない。

### SEC-01 資産保存と不正な資産生成の拒否

- **対応要求**: P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 資産を保有する利用者と安全性を検証する開発者。
- **前提**: 仕様で定める金額の単位、範囲、実入金の認識規則と暗号学的前提が明示されている。
- **要件**: 資産保存を満たし、不正な資産生成を拒否する。送金では入力額と出力額、出金では入力額と残額と公開出金額、入金では実受領額と発行額の整合を検証する。金額範囲外、負の値を表す不正入力、整数や体の演算境界を利用する不正を拒否する。
- **受入条件**: 正常: 入金の実受領額と発行額、送金の入力額と出力額、出金の入力額と残額と公開出金額が整合する。異常: 範囲外、負の値を装った入力、整数のあふれや体の剰余を悪用した資産生成を拒否する。予期しないETH受領から無権限のUTXOを発行できない。
- **検証方法**: 金額範囲と演算境界を含む自動テスト、資産保存と実装適合の形式証明。実受領額、UTXOの債務、未計上ETHを分けて確認する。
- **限界と依存**: ガス代はFR-08に従い別計上する。正当な入金に基づく発行と、コントラクトのETH残高増加を同一視しない。

### SEC-02 所有者による認可と独立した使用

- **対応要求**: P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 現在の所有者、以前の送信者、認可のない第三者。
- **前提**: 所有者が自分の鍵を管理し、採用方式の認可に関する前提が成立する。
- **要件**: 正当な所有者の認可なしにUTXOを消費できない。送信者が知る情報だけでは受取人のUTXOを使用できず、受取人は受領後の使用に送信者の追加協力を必要としない。
- **受入条件**: 正常: 所有者が自分のUTXOを送金と出金に使用でき、受取人は送信者の協力なしで使用できる。異常: 他人の鍵や無認可の操作、送信者が作成時に知った情報だけによる受取人のUTXOの使用、運営者の特権による使用を認めない。
- **検証方法**: 受取人による独立使用、送信者と第三者による不正使用の自動テスト。認可モデル、認可対象との結び付け、実コードの形式証明。
- **限界と依存**: 所有者の秘密鍵の侵害や紛失からの救済は保証範囲外。所有者情報の公開自体は禁止しない。

### SEC-03 入力の存在確認と二重使用防止

- **対応要求**: P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: UTXOを使用する利用者と競合する要求の送信者。
- **前提**: コントラクトが未使用と消費済みの状態を管理し、対象チェーンの実行順序に従う。
- **要件**: 存在しないUTXO、消費済みUTXO、同じ要求内で重複した入力を拒否する。競合する要求でも同じUTXOを二度消費できない。
- **受入条件**: 正常: 存在する未使用UTXOを1回使用すると消費済みになる。異常: 不存在、消費済み、同一要求内の入力重複を拒否する。競合要求をいずれの順序で実行しても、同じUTXOに基づく2回の成功を許さない。
- **検証方法**: 再実行、重複入力、競合要求の順序を変えた自動テストと、消費状態の不変条件の形式証明。
- **限界と依存**: チェーン確定前の状態認識はOPS-04で扱う。競合要求の一方が成功すること自体は異常ではない。

### SEC-04 認可と操作意図の結合

- **対応要求**: P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 操作を認可する所有者と、認可済みデータを変更または再利用する第三者。
- **前提**: 仕様が認可対象、検証対象とチェーンやデプロイの識別範囲を定義している。
- **要件**: 認可と検証が、対象の入力、出力、受取先、公開出金先、金額などの意図に結び付いている。改ざん、不正な証明や署名、過去の認可の再利用、別チェーンや別デプロイへの流用による無断使用を拒否する。
- **受入条件**: 正常: 認可した入力、出力、受取先、公開出金先、金額でのみ操作が成立する。異常: これらの変更、不正な証明や署名、過去の認可の再利用、別チェーンや別デプロイへの流用により、無断使用や別の操作を成立させられない。
- **検証方法**: 対象フィールドを変える改ざんテスト、認可再利用と別環境への流用テスト、認可と検証入力の対応を含む形式証明。
- **限界と依存**: 具体的な署名形式、認可方式、識別子や符号化は仕様と設計で決める。未確定要求の再送と成功済み要求の再使用を区別する。

### SEC-05 失敗時の原子性と外部呼出しの安全性

- **対応要求**: P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 送金や出金を行う所有者、ETH受領コントラクト。
- **前提**: 外部呼出し、受取先の失敗、再入を含む振る舞いを仕様と形式モデルが扱う。
- **要件**: 操作の失敗時には、UTXOの消費、生成、資産移動の一部だけが確定した状態を残さない。ETH受取先の失敗、資金不足、不正入力を含める。出金先からの再入を含む外部呼出しでも安全性を維持する。失敗したトランザクションのガス代は取消対象外。
- **受入条件**: 正常: 受理された操作は必要なUTXOの消費、生成、資産移動を一体として完了する。異常: 受取先の失敗、資金不足、不正入力では部分確定を残さない。受取先が再入を試みても無断使用、二重使用、資産生成や不整合な中間状態を確定できない。失敗時のガス代は戻らなくてもよい。
- **検証方法**: 操作前後のUTXOと資産状態を比較する自動テスト、失敗する受取先と再入を試みる受取先のテスト、外部呼出しを含むモデルと実装の形式証明。
- **限界と依存**: 原子性は対象の資産操作に関する保証であり、失敗トランザクションのgas支出まで取り消す要件ではない。再入の具体的な制御方式は選定しない。

### SEC-06 秘密情報の保持と公開範囲

- **対応要求**: P-03「機密性と限界を評価できる」、P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 鍵を保持する利用者、CLIと配送処理の実装者、成果を公開する研究者。
- **前提**: 認可、復号、受領確認に必要な秘密と、それぞれの保持者を仕様で識別している。
- **要件**: 鍵と非公開の受領情報の保持、受け渡し、利用の前提を明示する。秘密鍵や復号に必要な秘密を、オンチェーンや共有する成果物、通常の診断ログへ平文で出さない。本人への金額表示と研究用に意図的に公開する既知値は区別する。
- **受入条件**: 正常: 本人が金額を確認でき、受領情報を保護して利用できる。異常: 秘密鍵や復号に必要な秘密がオンチェーン、共有成果物、通常の診断ログへ平文で出る場合は不合格とする。意図的な試験用既知値の公開は、その目的と範囲を明示する。
- **検証方法**: チェーンへ送るデータ、CLI出力と診断ログ、成果物の内容を自動テストで確認し、秘密の保持と配送の処理を再実行して確認する。
- **限界と依存**: 本人の金額表示と公開診断ログを区別する。通信監視や端末侵入対策は対象外だが、秘密を平文公開してよいという意味ではない。

### 資産保存に含める残高と境界

未使用UTXOに対応する利用者への債務と、その裏付けとなるETHを区別して記述する。
コントラクトが予期しないETHを受け取る場合も扱い、その受領だけから不正なUTXO発行を認めない。
UTXOとして計上しないETHがあり得るため、「コントラクト残高と未使用UTXO総額は常に厳密に等しい」という条件だけで資産保存を定義しない。
正当な入金として認識する条件、未計上ETHの扱い、金額範囲と演算境界は、SEC-01を満たす形で仕様化する。

## 形式証明の要件

形式証明は状態モデルと実装適合の両方を必須とし、本体に含める暗号検証器を対象に含める。

### FV-01 状態モデルの機械検証

- **対応要求**: P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 形式モデルを作成する開発者と証明を再検証する第三者。
- **前提**: 入金、送金、出金、認可、未使用と消費済みの状態、外部呼出しと失敗を扱うモデルと、明示された信頼前提がある。
- **要件**: 入金、送金、出金の状態モデルについて、資産保存、正当な認可、二重使用防止、失敗時の状態保持を機械検証する。正常な操作が成立する条件も示し、すべてを拒否するだけのモデルで要件を満たしたと扱わない。
- **受入条件**: 正常: 資産保存、正当な認可、二重使用防止、失敗時の状態保持の命題が機械検証を通り、FRの正常操作が成立する条件も示される。異常: すべての操作を拒否するだけのモデルや、証明したい結論を前提にした証明では合格にしない。
- **検証方法**: モデル、命題、前提と機械検証ログを公開し、第三者が同じ手順で再検証する。正常操作の成立と安全性の命題を両方確認する。
- **限界と依存**: モデルの証明のみでは本体実装の適合を保証しない。FV-02とFV-03も必須。

### FV-02 本体実装のモデル適合

- **対応要求**: P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 本体を実装する開発者と形式検証を再実行する第三者。
- **前提**: FV-01のモデルと、対象とする本体の実コードとコミットが固定されている。
- **要件**: 本体の資産管理、認可、入力検証、UTXOの消費と生成、外部呼出しと失敗時の処理について、実コードがモデルに従うことを機械検証する。検証器に渡す入力と実際の操作の対応、および検証結果に応じた受理と拒否を含める。
- **受入条件**: 正常: 資産管理、認可、入力検証、UTXOの消費と生成、外部呼出し、失敗処理について、実コードがモデルに従うことを機械検証できる。実際の操作と検証器へ渡す入力、および検証結果と受理または拒否が対応する。異常: モデルだけの証明と手作業の対応表で代替する場合や、必須経路を除外した場合は不合格とする。
- **検証方法**: モデルと実コードの対応に関する命題、対象範囲、検証手順と機械検証結果を公開する。対象コミットとの一致を再検証する。
- **限界と依存**: 検証手法とツールは未選定。扱えないコードがある場合に黙ってテストだけへ置換しない。

### FV-03 暗号検証器と検証関係の適合

- **対応要求**: P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 暗号検証器と本体固有の検証関係を実装する開発者。
- **前提**: 採用する暗号の検証規則と、本体が要求する資産保存や認可を表す回路または検証関係が仕様化されている。
- **要件**: 本体に含める暗号検証器のコードが、仕様の検証規則に適合することを機械検証する。検証器全体を「常に正しく判定する部品」と仮定するだけでは、この要件を満たさない。
- **受入条件**: 正常: 本体の暗号検証器の実コードが検証規則どおりに判定することと、本体固有の回路や検証関係がモデルの必要条件を表すことを機械検証できる。異常: 検証器全体を常に正しい部品と仮定したり、本体固有の検証関係と安全性条件の対応を未証明のまま前提にしたりする場合は不合格とする。
- **検証方法**: 検証規則、実コード、回路や関係、モデルの命題を結ぶ機械検証を公開し再実行する。信頼する暗号プリミティブと証明対象の境界も点検する。
- **限界と依存**: 暗号方式自体の健全性や機密性を暗号学的仮定から形式証明することは初期必須ではない。証明生成プログラムをテスト対象にすることを理由に、本体固有の関係の適合を除外しない。

### FV-04 証明の追跡可能性と再検証

- **対応要求**: P-04「第三者が実装と評価を再現して検証できる」、P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 証明の作成者、第三者の検証者。
- **前提**: 要件IDと必須命題、モデル、対象コード、依存関係、信頼前提の一覧がある。
- **要件**: 要件ID、命題、モデル、対象コードとコミット、信頼前提を対応付ける。ツールと依存関係の版、設定、検証手順を固定し、第三者が全必須命題を再検証できる。
- **受入条件**: 正常: 固定したツール版、依存版、設定、手順で全必須命題を再検証でき、対象コミットと要件IDへの対応が確認できる。異常: 証明穴、証明対象そのものの公理化、検証の無効化、未実行やスキップ、タイムアウト、未判定を合格扱いしない。
- **検証方法**: 命題ごとの成否と対応表を出力し、依存先を含む未証明箇所と公理を確認する。第三者が公開環境で全必須命題を再実行する。
- **限界と依存**: 標準的な論理公理、暗号仮定、EVMやコンパイラ等の信頼対象は列挙し、証明結果の条件として扱う。ツール名だけで実装全体が証明済みとはしない。

### 機械検証の対象と信頼境界

| 対象 | 必須の確認 | 境界 |
| --- | --- | --- |
| 状態モデル | 資産保存、認可、二重使用防止、失敗時の状態保持、正常操作の成立条件 | モデルだけの証明では完了しない |
| 本体実コード | モデルに従うこと。検証入力、結果の利用、外部呼出しと失敗処理も含む | 手作業の対応表は補助資料であり機械検証の代替ではない |
| 本体の暗号検証器コード | 仕様の検証規則に従うこと | 検証器全体を信頼する仮定に置き換えない |
| 本体固有の回路や検証関係 | モデルが要求する資産保存、認可等の条件に対応すること | 暗号方式の安全性仮定と、本体の必要条件を正しく検証する関係であることを区別する |
| 暗号方式自体の安全性 | 採用根拠と仮定を説明 | 健全性や機密性の暗号学的な形式証明は初期必須ではない |
| CLI、証明生成プログラム、受領データの配送コード | 自動テストと第三者による再現と検証 | これらのプログラムの形式証明は必須ではない。本体固有の回路や関係は上記の証明対象 |
| プリミティブ、EVM、コンパイラ、外部ライブラリ、論理公理 | 何を信頼し、どこまで証明したかを明記 | 依存先を含めて未証明箇所を確認する。本体の検証器全体を外部依存と呼んで除外しない |

## 金額の機密性と推論評価

金額の秘匿の根拠と、公開された収支や取引関係からの推論による漏えいを別々に説明する。
どの観測者に何が分かるかを明示し、すべての送金で金額が推論不能になるとは主張しない。

### PRIV-01 暗号学的な金額の秘匿と公開情報

- **対応要求**: P-03「機密性と限界を評価できる」。
- **区分**: 必須。
- **対象者**: 金額を秘匿したい利用者と、公開チェーン情報を観測する第三者。
- **前提**: 採用する暗号方式とその安全性の前提、チェーンへ公開する情報が明示されている。
- **要件**: 機密送金の金額を平文で公開せず、公開されるコミットメント、証明、受領データについて、明示した暗号学的前提の下で金額を秘匿できる根拠を示す。可逆な符号化だけで秘匿を満たしたと扱わない。取引関係、入出金額、送信元や所有者に関する情報、ガスや受領データなどの公開メタデータを列挙し、収支推論による金額の判明とは区別する。
- **受入条件**: 正常: 金額を平文公開せず、コミットメント、証明、暗号化された受領データから金額を秘匿する根拠を説明できる。公開される取引関係、入出金額、送信元や所有者情報、gas、配送データ等を列挙できる。異常: 可逆な符号化のみ、受領データ等からの平文漏えい、収支推論と暗号の秘匿を混同した説明は不合格とする。
- **検証方法**: 採用方式の一次資料と仮定、公開データの一覧、実装が扱う公開情報と秘密の対応を示す。実データによる漏えい確認と推論シナリオを再実行して結果を確認する。
- **限界と依存**: 暗号的な秘匿があっても公開グラフと既知額から金額が判明し得る。取引関係と所有者情報の秘匿は必須ではない。

### PRIV-02 観測者別の金額推論の再現

- **対応要求**: P-03「機密性と限界を評価できる」。
- **区分**: 必須。
- **対象者**: 公開情報だけの観測者と、取引相手の情報も知る観測者、評価を再実行する研究者。
- **前提**: 観測情報、推論対象のUTXOや取引金額、追加情報の出所と内容をケースごとに固定している。
- **要件**: 公開チェーン情報だけを見る第三者と、取引相手が知る金額などを追加で知った第三者を比較する。観測情報、対象金額、推論条件を明記し、金額が一意に判明するケースと複数候補が残るケースをそれぞれ再現する。
- **受入条件**: 正常: 公開情報だけの場合と取引相手の既知額等を加えた場合を比較し、一意に判明するケースと複数候補が残るケースをそれぞれ再現できる。異常: 観測者に与えていない秘密を推論に使う、他の公開メタデータを無視して機密性を断定する、複数候補のケースを示せない場合は不合格とする。
- **検証方法**: 取引グラフ、観測者へ与える情報、収支条件、推論結果をスクリプトとともに公開する。候補のある評価で他の公開情報が与える制約も説明する。
- **限界と依存**: 候補は観測者の収支推論上の候補であり、単一コミットメントの複数の正しい開示値を意味しない。算術的な不確定性だけでは公開情報全体に対する機密性の証拠にならない。

### PRIV-03 追加情報と後続操作による推論の変化

- **対応要求**: P-03「機密性と限界を評価できる」。
- **区分**: 必須。
- **対象者**: 過去と現在の公開履歴を観測する第三者と評価者。
- **前提**: 同じ対象金額について、追加情報を得る前後の観測条件を比較できる。
- **要件**: 追加情報や後続の出金により、過去の送金額について推論できる内容が変わるケースを示す。候補の金額範囲を示せるケースではその範囲も示すが、全ケースの厳密な候補数計算は必須にしない。
- **受入条件**: 正常: 取引相手の既知額や後続の公開出金によって、過去の送金額の候補が絞られるケースを再現できる。候補範囲を示せるケースでは範囲も記録する。異常: 公開済み履歴を後から消せると仮定した評価や、追加情報を得た後も以前の候補をそのまま保証する評価は不合格とする。
- **検証方法**: 同一の取引履歴に情報を段階的に追加する再現スクリプトで、対象金額の推論結果と可能な範囲の変化を出力する。
- **限界と依存**: 全ケースの厳密な候補数の計算は必須ではない。通信監視や端末侵入による情報取得への対策は保証範囲外とする。

### 必須の推論シナリオ

評価では、次の各ケースについて観測情報と推論結果を再現する。
ガス代をUTXOから差し引かず、各例の入出力と公開資産移動をすべて列挙する。

| ケース | 観測情報と対象 | 追加情報 | 期待する評価 |
| --- | --- | --- | --- |
| 既知入金からの全額移転 | 入金から入力額10が既知であり、送金先の出力以外に金額を持つ出力や資産移動がないと分かる。対象はその出力額 | なし | 保存条件から出力額10が一意に判明することを再現 |
| 2出力への分割 | 既知入力10を2出力aとbに分ける。対象はa。公開収支はa+b=10 | なし | 収支だけでは複数候補があることを示し、他の公開情報と暗号の前提も検討して残る不確定性を説明 |
| 取引相手の既知額の追加 | 上記と同じ分割と対象 | 取引相手からa=3と判明する情報 | a=3、b=7へ絞られることを、公開情報だけの観測者と比較 |
| 後続の公開出金 | 上記のaのUTXOを、他の入力や残額を伴わず全額出金したことが公開グラフ等から分かる | 公開出金額3 | 過去のa=3とb=7が推論できるようになることを、出金前と比較 |

分割の例で、説明上の候補を正の整数に限ればaは1から9までの候補を持つ。
この説明は金額の最小単位、ゼロ出力の可否、プロトコルの具体的な範囲を決めるものではない。
実際の評価では仕様の範囲と各観測条件を用い、示せる候補範囲を報告する。

収支の候補が複数であることと、暗号コミットメントに複数の正しい開示値があることを混同しない。
所有者情報や受領データ、gasなどから候補が絞られる場合も結果に反映する。
収支式だけの曖昧さをもって公開情報全体への機密性を保証しない。
採用する方式で複数候補が残るケースを示せなければP-03未達とし、理由を記録してPRDまたは方式を見直す。

## 比較評価と測定

比較の合格条件は、条件と限界を説明できる実測比較が成立することである。
本方式のgasや証明生成時間が先行方式より優れることは合格条件にしない。
期待した利益が得られない場合も結果を残し、要求や方式を見直す判断材料とする。

### EVAL-01 比較対象の採用と代替条件

- **対応要求**: P-02「利用に必要なコストを先行方式と比較評価できる」。
- **区分**: 必須。
- **対象者**: 本体と先行方式を比較する開発者や研究者。
- **前提**: 比較対象のコード、実際の証明生成経路とオンチェーン暗号検証経路を特定できる。
- **要件**: 少なくとも1方式と、実際の証明生成とオンチェーンの暗号検証を伴う比較を行う。[EIP-8182](https://eips.ethereum.org/EIPS/eip-8182)の[公開参照実装](https://github.com/0xFacet/eip-8182-reference-implementation)を第一候補とする。再現できない場合は、試した版と条件、失敗理由を記録し、同じ採用条件を満たす別方式へ切り替えられる。
- **受入条件**: 正常: EIP-8182の公開参照実装を第一候補として実行し、条件を満たす少なくとも1方式と実測比較できる。異常: 第一候補を再現できない場合は、試したコミットや版、環境、失敗理由を残し、同じ条件を満たす別方式へ切り替える。モックや資料の参考値の転記だけでは合格にしない。
- **検証方法**: 採用候補の実行経路、再現用コマンド、生成した証明の検証結果、本体との測定結果と生データを確認する。
- **限界と依存**: 比較対象の採用には、実際の証明生成とオンチェーン検証を再実行できることを要する。網羅的な比較は不要だが、比較対象がゼロの状態は合格にしない。

### EVAL-02 操作全体のgasと証明生成時間

- **対応要求**: P-02「利用に必要なコストを先行方式と比較評価できる」。
- **区分**: 必須。
- **対象者**: 比較測定を実施する開発者と結果を読む研究者。
- **前提**: 本体と比較対象について、操作、認可方式、証明生成器、測定経路と範囲を固定している。
- **要件**: 入金、送金、合算を伴う送金、出金の測定ケースを用意する。操作の成立に必要な認可、検証、状態更新、受領データを含む取引全体のgasと、必要な証明生成時間を測る。初回登録、デプロイ、セットアップや前処理の費用は通常操作と区別して記録する。
- **受入条件**: 正常: 入金、送金、合算を伴う送金、出金について、必要な認可、暗号検証、状態更新、受領データを含む取引全体のgasと必要な証明生成時間を記録できる。異常: 検証を省略した結果や、別々の認可構成のgasと生成時間を同一構成として組み合わせた結果を合格にしない。
- **検証方法**: receipt等の実行記録と証明生成の時間計測を、構成とケースごとに対応付ける。初回登録、デプロイ、セットアップ、前処理を別の費用として記録する。
- **限界と依存**: 先行方式より安い、速いという閾値は設けない。非対応操作はEVAL-03に従い比較不能と明記する。

### EVAL-03 配送コストと機能差を含む比較

- **対応要求**: P-02「利用に必要なコストを先行方式と比較評価できる」、P-03「機密性と限界を評価できる」。
- **区分**: 必須。
- **対象者**: コストと利用条件を評価する開発者や研究者。
- **前提**: 各方式が提供するシナリオ、機密性、信頼前提、資産と入出力条件が分かる。
- **要件**: 受領データの掲載によるgas、配送用データの生成、同期と復号の処理負担も評価に含める。比較対象が同じ利用シナリオを提供できるか確認し、機能、機密性、信頼前提、対象資産、入出力数、ダミー出力やバッチ化の違いを併記する。
- **受入条件**: 正常: 受領データ掲載のgas、配送用データ生成、受信側の同期と復号の処理負担を測定範囲に含め、操作全体との関係を示せる。対象資産、入出力数、ダミー出力、バッチ化、機能、機密性、信頼前提の差を結果に併記できる。異常: 同じシナリオを提供できない方式を理由の記載なしで同等扱いしたり、必須の配送負担を隠したりする場合は不合格とする。
- **検証方法**: 操作と機能の対応表、費用内訳、生成と同期と復号の測定結果を公開する。非対応のシナリオは比較不能の理由を示す。
- **限界と依存**: 受領データの掲載gasは取引全体の内数として扱い、合算時の二重計上を避ける。観測する履歴量など、配送測定に影響する条件もEVAL-04で固定する。

### EVAL-04 測定条件の固定と生データ

- **対応要求**: P-02「利用に必要なコストを先行方式と比較評価できる」、P-04「第三者が実装と評価を再現して検証できる」。
- **区分**: 必須。
- **対象者**: 測定を実施する人と検証を再実行する第三者。
- **前提**: 測定前に環境、入力と集計方法を記録できる。
- **要件**: 仕様版、実装コミット、認可方式、証明生成器、ツールと依存版、ハードウェア、EVM設定、入力条件、初回と反復時の状態、測定範囲、反復回数、集計方法を測定前に固定する。生データと再現スクリプトを提供する。
- **受入条件**: 正常: 仕様版、実装コミット、認可方式、証明生成器、ツールと依存版、ハードウェア、EVM設定、入力条件、初回と反復時の状態、測定範囲、反復回数、集計方法を固定し、生データと再現スクリプトを提供できる。異常: 構成不明、都合のよい測定値のみの選別、必要な検証のスキップを隠した集計を合格にしない。
- **検証方法**: 測定条件と実行記録を照合し、第三者が同じ条件のローカル環境で反復測定と生データからの集計を再実行して結果を確認する。
- **限界と依存**: 具体的な入力値、反復回数、統計量、資源上限は評価計画で定める。異なる環境の値を無条件に同じ数値へ一致させる要件ではない。

### 測定に必要な記録

| 区分 | 固定し、記録する内容 |
| --- | --- |
| 実装と暗号の構成 | 仕様版、実装コミット、認可方式、証明生成器、実際に通る検証経路、ツールと依存関係の版 |
| 環境 | ハードウェア、EVMの設定、必要な資源、実行環境の設定 |
| ケースと状態 | 入金、送金、合算、出金、対象資産、入出力数、ダミー出力、バッチ化、入力値、初回と反復時の状態 |
| 測定の範囲 | 取引全体のgas、必要な証明生成、配送用データ生成、同期と復号。同期対象の履歴量など処理負担を左右する条件 |
| 初回と準備の負担 | 初回登録、デプロイ、セットアップ、前処理。通常操作との関係と、反復に再利用できる範囲 |
| 集計と根拠 | 測定前に決めた反復回数と集計方法、生データ、再現スクリプト、非対応や失敗の理由 |
| 解釈 | 機能、機密性、信頼前提の差、比較できる操作とできない操作、結果が適用できる条件 |

## 実行環境と再現手順

### OPS-01 ローカルでの自動検証と再現

- **対応要求**: P-04「第三者が実装と評価を再現して検証できる」、P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 本体と比較対象を構築する開発者、検証を再実行する第三者。
- **前提**: 公開した版と設定のローカルEthereum環境と、証明を再検証する環境を用意できる。
- **要件**: ローカルEthereum環境で基本操作、正常系と異常系の自動テスト、比較ベンチマークを再現できる。形式証明も公開した環境と手順で再検証できる。
- **受入条件**: 正常: 基本操作、正常系と異常系の自動テスト、反復可能な比較ベンチマークを再実行できる。全必須命題も公開した環境で再検証できる。異常: 手作業のみの確認、テストのスキップ、証明の未判定、実暗号を省いた比較で合格を代替しない。
- **検証方法**: CLIとスクリプトで操作、テスト、測定、証明再検証を実行し、それぞれの成否と対象版を記録する。
- **限界と依存**: 形式証明のツールはEthereumノードと別の実行環境でもよい。公開テストネットで全テストや比較対象の反復測定を行うことは必須ではない。

### OPS-02 公開テストネットでの本体検証

- **対応要求**: P-01「機密UTXOによる資産移転を利用できる」、P-04「第三者が実装と評価を再現して検証できる」、P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: 本体の検証を実行する開発者と公開記録に基づいて動作を再確認する第三者。
- **前提**: 少なくとも1つのEthereum公開テストネットで、テスト用ETH、RPCまたはノード、対象コードを利用できる。
- **要件**: 少なくとも1つのEthereum公開テストネットに本体をデプロイし、入金、部分送金、合算、受取人による再送金と出金、代表的な不正操作の拒否を確認する。ネットワーク、対象コード、デプロイ先アドレス、取引記録、実測gasを公開する。比較対象を含む反復ベンチマークはローカルを必須とする。
- **受入条件**: 正常: 本体をデプロイし、入金、部分送金、合算、受取人による再送金と出金を実行できる。代表的な不正操作の拒否を確認し、ネットワーク、対象コード、アドレス、取引記録と実測gasを公開できる。異常: ローカルだけの成功や、公開デプロイだけで一連の操作を確認していない状態を合格にしない。
- **検証方法**: 成功取引の記録とgas、無断使用や二重使用など代表的な拒否を確認した呼出しまたは取引の記録を、シナリオと要件IDへ対応付ける。
- **限界と依存**: 比較対象も含めた反復ベンチマークはローカルが必須。ネットワーク名と確定条件は設計で選定する。

### OPS-03 第三者向けの実行手順と前提

- **対応要求**: P-04「第三者が実装と評価を再現して検証できる」。
- **区分**: 必須。
- **対象者**: 公開された資料に基づいて検証する第三者の開発者や研究者。
- **前提**: 公開されたリポジトリ、必要なソフトウェアと資源、テスト用ETH、必要なチェーン履歴へアクセスできる。
- **要件**: 必要なソフトウェア、資源、設定、テスト用ETHの入手条件、保持する鍵、アクセスが必要な履歴を記載し、第三者がCLIとスクリプトで操作と検証を再実行できる。実資金は使わない。
- **受入条件**: 正常: 必要なソフトウェア、版、資源、設定、テスト用ETHの入手条件、保持する鍵、必要な履歴を手順から把握し、CLIとスクリプトで操作と検証を再実行できる。異常: 作成者だけが持つ非公開設定や鍵、専用配送サービス、実資金を要求する手順は不合格とする。
- **検証方法**: 公開手順のみを用い、第三者が用意した鍵とテスト用資産で環境構築から検証まで再実行する。
- **限界と依存**: 通常のノードやRPCから必要な履歴を取得できることは外部依存。特定RPC事業者の永続稼働やテストネットの永続存続を仮定しない。

### OPS-04 確定状態の確認と再同期

- **対応要求**: P-04「第三者が実装と評価を再現して検証できる」、P-05「利用者の資産を正当に扱う」。
- **区分**: 必須。
- **対象者**: CLIを使う送信者と受取人。
- **前提**: 採用する確定条件と、未確定、失敗、確認できない状態を仕様で区別する。
- **要件**: 通信失敗や未確定の取引を、成功や利用可能な受領として表示しない。採用する確定条件、再同期、失敗後の再試行で状態を確認する方法を定める。専用配送サービスの稼働は受領の前提にしない。
- **受入条件**: 正常: 確定条件を満たした操作のみを成功または利用可能な受領として扱い、再同期や失敗後の再試行前にチェーンの状態を確認できる。異常: RPC通信失敗や未確定の取引を成功と表示しない。確認不能を未実行と決めつけて再使用や二重計上を行わない。
- **検証方法**: 通信中断、未確定、失敗後の再確認、履歴の再取得を扱うCLI自動テストと、確定状態との照合。
- **限界と依存**: 再同期には鍵と公開履歴を用いる。専用配送サービスの稼働を前提にしない。本番の可用性SLAや鍵紛失時の復旧を保証しない。

### OPS-05 研究成果の公開条件

- **対応要求**: P-02「利用に必要なコストを先行方式と比較評価できる」、P-03「機密性と限界を評価できる」、P-04「第三者が実装と評価を再現して検証できる」。
- **区分**: 必須。
- **対象者**: 初期成果を公開する開発者や研究者と評価するコミュニティ。
- **前提**: 実装と比較ベンチマークの結果、再現方法、比較条件、機密性の評価と限界を説明できる資料がある。
- **要件**: 実装と比較ベンチマークの結果を、再現方法、比較対象、測定条件、機密性と機能の違い、評価の限界とともにethresear.chへ公開する。機密性とコストの評価結果に基づき、有望な利用条件、適さない条件、未判断事項を整理し、その根拠とともに示す。
- **受入条件**: 正常: 初期成果としてethresear.chへ公開する内容に、実装、実測結果、再現方法、比較対象、測定条件、機密性と機能の違い、評価の限界を含める。用途への適合性に関する各判断を推論評価や実測結果と対応付け、有望な利用条件が見つからない場合もその旨を記載する。異常: 未測定の優位性、未確認の実装や証明の完成、根拠のない用途への適合性を断定したり、条件や限界、用途への適合性の考察を欠いたりする公開内容を合格にしない。
- **検証方法**: 公開内容と対応するコード、実測生データ、再現手順、要件ごとの成否を照合する。用途への適合性に関する判断の根拠を、推論評価や実測結果と照合する。未達や期待した利益が得られない結果も区別して示す。
- **限界と依存**: 公開する結果の適用範囲は、対象コード、測定条件、機密性の前提に限定する。

## 仕様と設計で定める事項

以下の事項を、関連する要件の制約と受入条件に基づいて定める。
規則と振る舞いは仕様書、実現方法と採用理由はDesign docに記載する。

| 決める事項 | 決定する段階 | 満たす制約と関連要件 | 判断が影響する範囲 |
| --- | --- | --- | --- |
| 暗号方式と安全性の前提 | 設計で採用理由を比較し、仕様で検証規則を固定 | SEC-01〜SEC-04、PRIV-01、FV-03。実暗号、所有者認可、金額範囲、秘匿の根拠を満たす | 信頼対象、コスト、検証器の実装と形式証明 |
| 数式、証明関係、回路 | 仕様 | 資産保存と認可等のモデル条件に対応することをFV-01〜FV-03で機械検証 | 証明生成、検証器、実装適合と安全性 |
| 金額の単位、範囲、符号化、入金の認識規則 | 仕様 | FR-01〜FR-04、SEC-01。部分操作と合算が可能で、範囲外や演算境界を悪用できない | 入出力検査、資産保存、推論評価 |
| API、イベント、エラー | 仕様 | FR-01〜FR-08、SEC-04〜SEC-05、OPS-04。意図との結合、原子性、失敗の識別 | CLI、操作の認可、呼出し元との連携 |
| UTXOの状態構造 | 仕様で状態と遷移、設計で具体的構成 | コントラクトストレージ管理、公開グラフ、SEC-03、FV-02 | gas、消費確認、モデルと実コードの対応 |
| 受取情報と暗号化受領データの形式、検索と配送 | 仕様で形式と必要動作、設計で暗号と構成 | FR-05〜FR-07、SEC-06、PRIV-01、EVAL-03。鍵と公開履歴で受領でき、毎回の手動配送を要求しない | 同期負担、gas、秘密の保持、金額推論 |
| 入出力数の上限、ゼロ値やダミー出力の規則 | 仕様 | FR-02〜FR-04の最低シナリオとSEC-01を満たす。比較条件にも反映 | 証明サイズ、gas、機能比較、推論の候補範囲 |
| 証明ツールと実コードの対応方法 | 設計で実現可能性を確認し、証明対象を仕様と対応付ける | FV-01〜FV-04。本体実装と暗号検証器を証明できること | 実装言語やライブラリ、検証可能なコード範囲、信頼対象 |
| 実装言語、ライブラリ、CLIと測定の構成 | 設計 | FR、SEC、FV、EVAL、OPSの全必須要件を満たす | 開発環境、検証の再現条件、依存関係、資源 |
| 公開テストネット、RPCや履歴のアクセス条件 | 設計と実行手順 | OPS-02〜OPS-03。少なくとも1つのEthereum公開テストネット、実資金なし | テスト用ETH、デプロイ、取引記録、検証の再現手順 |
| 確定条件、未確定や通信失敗の表示、再同期 | 仕様、実行環境ごとの設定は設計と手順 | FR-07、OPS-04。未確定を成功扱いせず再試行時に状態を確認 | CLIの状態認識、二重計上防止、受領可能になる時点 |
| 比較対象の採用版と実行経路 | 設計と評価計画 | EVAL-01〜EVAL-03。EIP-8182を第一候補とし、実際の証明生成と検証を再実行 | 機能差、認可方式、比較不能範囲、測定結果の解釈 |
| 測定入力、反復回数、集計方法 | 評価計画で測定前に固定 | EVAL-04。初回と反復、測定範囲、生データ、再現手順を公開 | 再現性、比較の公平性、必要な計算資源 |
