# Uniswap接続の要件定義

## 目的と位置付け

[Uniswap接続のPRD](PRD.md)のU-01〜U-07を、実装と検証の計画を作れる受入条件へ具体化する。
[Issue #13](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/13)の2026年9月26日の合意を反映する。
基準PRDのコミットは`ca00bd8e43874b9a09bf8be1b2ad71ecaf44ef53`であり、作成時に確認したmainも同じ版だった。

本書の完成は要件定義の完了を意味する。
接続仕様、設計、実装、実測、形式証明、応募手続きが完成したことは意味しない。
以下の受入条件と必要な証拠は、後続の実装・評価で満たす条件である。
本体の保証は[本体要件定義](../../requirements.md)と[本体仕様](../../specification.md)を正本とし、本書では接続固有の条件と組合せの保証を定める。

## 対象範囲と共通前提

| 項目 | 必須範囲・制約 |
| --- | --- |
| 利用者と用途 | 機密ETHで報酬を受け取った個人が、その一部を公開トークンで相手へ支払い、残額を再送金する |
| 最小入力 | 単一所有者の単一UTXOからの部分支払い。入力額を`V`、使用ETH額を`w`とし、`0 < w < V`、残額を`r = V - w`とする |
| 交換と着金 | 認可した固定額`w`を全額交換し、一種類の公開トークンの交換出力全量を、指定した最終受取人へ最低受取額以上届ける |
| 認可 | 使用ETH額、交換先トークン、最低受取額、最終受取人、有効期限を、所有者の出金認可に結び付ける |
| 残額とgas | `r`は支払者の機密ETH UTXOに保持する。gasは別途公開ETHから支払い、`V`、`w`、`r`へ混ぜない |
| 成果の提供 | CLIと再現スクリプト。正常経路は本体の実暗号検証、選定したUniswapコントラクトでの交換、テスト用資産の実移動を伴う |
| 実行環境 | ローカルEthereumと、少なくとも1つのEthereum公開テストネット。実資金を扱わない |
| 検証強度 | 接続の正常・異常系の自動テストを必須とする。接続固有の形式証明は後続課題とし、本体のFV-01〜FV-04は維持する |
| 評価 | 公開情報からの推論の対照例と、通常の公開交換との実測比較。費用の数値上限や優位性は合格条件にしない |
| 未実証の依存 | 本体の完成実装、交換固有条件と本体認可の結合、公開テストネットのUniswap構成と流動性を利用可能とは仮定しない |

複数入力と残額ゼロの全額支払いは接続の追加対応とし、最低必須範囲に含めない。
実装が追加の入力形態を受け付ける場合は、本書の認可、取消、資産保存、受領の保証を維持し、対応する検証を追加する。
未対応の形態は資産効果を残さず拒否する。本体の対応範囲は縮小しない。

GUI、厳密な請求額決済、交換額の秘匿、出力トークンの再秘匿、本体の多資産化、複数人の集約交換、ENS、組織の承認・会計、本番運用は対象外とする。
先行機密方式との接続比較や別の支払い例は任意とし、本体の比較評価要件を免除しない。
応募用PoCは本体全体の比較評価・形式証明の完了に先行してよいが、未完了要件を明示する。

## 用語と関係者

接続PRDの[支払いに関わる用語](PRD.md#支払いに関わる用語)を継承する。
所有者、提出者、ガス支払者の意味と対応は、本体の[用語と関係者](../../requirements.md#用語と関係者)と[トランザクションの提出と実行文脈](../../specification.md#トランザクションの提出と実行文脈)に従う。

| 用語 | 本書での意味 |
| --- | --- |
| 支払者 | 使用するUTXOの所有者として支払いを認可する利用者 |
| 最終受取人 | 交換後の公開トークンを受け取る相手。本体からETHを受け取る公開出金先とは区別する |
| 最低受取額 | 最終受取人へ届く必要があるトークン額の下限。厳密な請求額ではない |
| 残額 | 固定ETH使用額を差し引いて本体に保持する機密UTXOの金額。交換後の返金や公開トークンの余剰額を指さない |
| 支払い | 入力の消費、残額の生成、本体からの出金、交換、最終受取人への着金を組み合わせる資産操作 |
| 支払い試行 | 一つの認可済み支払いを成立させようとする実行。報酬の受領や後続の残額再送金とは別の段階 |
| 有効期限 | 支払者が認可する、支払いを成立させてよい期限。時刻の意味と比較境界は接続仕様で定める |
| 実受取額 | 当該支払いにより最終受取人が実際に受け取った、認可されたトークンの額。交換処理が返す数値だけでは判定しない |

支払者の認可済み内容を別の提出者が提出すること自体は不正としない。
提出者に支払条件の変更権限を与えず、取りまとめ役への秘密の開示を必須経路の前提にしない。
報酬支払元、支払者、最終受取人が知る金額の違いは、UPRIV-02で評価する。

## 正常な利用の要件

### UFR-01 報酬の受領と使用可能性の確認

- **対応要求**: U-01、U-03、U-07。
- **区分**: 必須。
- **対象者**: 機密ETHの報酬を受け取る支払者。
- **前提**: 本体の受取情報、必要な鍵、公開履歴へのアクセス、テスト用資産と実行資源がある。
- **要件**: 報酬の機密送金を受領し、本人が金額と使用可能性を確認して、UFR-02の入力として利用できる。
- **受入条件**: 正常: 確定した報酬UTXOを鍵と公開履歴から確認し、報酬支払元の追加協力なしで支払いへ使える。異常: 未確定、復号不能、不整合な受領を利用可能資産へ計上しない。同じ履歴の再取得で二重計上しない。
- **検証方法**: 本体の受領処理を使うCLIの一連の実行と、受領状態の自動テスト。受領前に報酬支払元を停止したケースも確認する。
- **必要な証拠**: 報酬送金と確定状態、UTXOの識別、本人による金額・整合性確認、後続支払いとの対応、異常系の成否。本人向けの金額表示と公開ログを区別する。
- **限界と依存**: 本体FR-05〜FR-07、SEC-06と[受領の保証](../../specification.md#受領の保証と不整合な受領データ)に依存する。本体の受領機能を接続側に再実装する要件ではない。

### UFR-02 固定ETH額の交換と全量着金

- **対応要求**: U-01、U-03、U-07。
- **区分**: 必須。
- **対象者**: 支払者と最終受取人。
- **前提**: UFR-01の単一UTXO、USEC-01の有効な認可、交換に必要な流動性、対応トークンと受取人、公開ETHによるgasがある。
- **要件**: `w`を全額交換し、認可されたトークンの交換出力全量を最終受取人へ渡す。実受取額が最低受取額以上で、入力消費と支払者の残額`r`の生成が整合した場合に成功とする。
- **受入条件**: 正常: 指定した受取人の実受取額と交換出力全量の一致、最低受取額以上の着金、`V = w + r`、入力の一度だけの消費を確認できる。異常: 別トークン・別受取人への送付、最低額未達、一部だけの交換・着金、支払い由来資産の意図しない中間残留を成功にしない。入力不足や未対応形態も資産効果を残さず拒否する。
- **検証方法**: 実暗号とUniswapの交換を通る正常系、最小境界と未対応入力、着金不足・中間残留の異常系テスト。選定トークンの挙動に沿って実移動を照合する。
- **必要な証拠**: 認可された条件、入力と残額の対応、交換へ投入したETH額、交換出力と最終着金の照合、関連する資産状態の前後比較、対象コードと取引記録。
- **限界と依存**: 本体FR-04、FR-08、SEC-01と[基本操作](../../specification.md#基本操作)、[ガスと資産移動の会計](../../specification.md#ガスと資産移動の会計)に依存する。着金判定の意味は接続仕様、トークンの挙動と計測方法は設計で具体化する。戻り値、イベント、外側取引の成功だけで実受取額の証拠を代替しない。

### UFR-03 残額の確認と再送金

- **対応要求**: U-01、U-03、U-07。
- **区分**: 必須。
- **対象者**: 支払者と残額の再送金先。
- **前提**: UFR-02の支払いが確定し、支払者が受領に必要な鍵と公開履歴を持つ。
- **要件**: 支払者が残額`r`を自分の利用可能UTXOとして確認し、別の所有者へ再送金できる。
- **受入条件**: 正常: 残額の金額と所有者が整合し、再送金先が受領して使用可能性を確認できる。異常: 消費済み入力の残高への再計上、残額の二重計上、第三者による無認可使用、受領不能な残額を正常と扱わない。
- **検証方法**: 支払い後の同期、残額再送金、再送金先の受領をCLIで実行し、履歴の再取得と無認可使用を自動テストする。
- **必要な証拠**: 支払い・残額生成・再送金・再送金先の受領の対応、各段階の確定状態、本人による金額と使用可能性の確認。
- **限界と依存**: 本体FR-02、FR-05〜FR-07、SEC-02に依存する。残額を使用できることは、その金額が推論されないことを意味しない。報酬受領、支払い、残額再送金はそれぞれ確定する段階であり、全履歴を一体に取り消す要件ではない。

## 認可と安全性の要件

### USEC-01 支払条件と出金認可の結合

- **対応要求**: U-04、U-02、U-07。
- **区分**: 必須。
- **対象者**: 支払者、提出者、接続の実装者。
- **前提**: 本体の所有者認可と、実行対象の支払いとの対応を確認できる経路を設計する。
- **要件**: 使用ETH額、交換先トークン、最低受取額、最終受取人、有効期限を所有者の出金認可に結合し、認可された意図だけを成立させる。実行時に入力状態と期限の有効性を確認する。
- **受入条件**: 正常: 有効な認可と現在の入力状態で意図どおりの支払いが成立し、経路の条件を満たす別提出者も同じ内容を提出できる。異常: 五つの条件の各改ざん、認可の偽装・別出金への付替え、別チェーン・別デプロイへの流用、期限切れを拒否する。先行する認可検証の成功だけで、失効後の実行を許可しない。
- **検証方法**: 条件を一項目ずつ変更するテスト、別出金・別環境のテスト、期限の前・境界・後のテスト、検証後に期限が失効するケースを実暗号で確認する。
- **必要な証拠**: 変更前後の公開条件と対象操作、認可と出金・交換の対応、実行時の期限判定、拒否理由、資産効果が残らない記録。秘密を公開する必要はない。
- **限界と依存**: 本体FR-09、SEC-02、SEC-04と[認可対象](../../specification.md#認可対象)、[認可結果の検証](../../specification.md#認可結果の検証)に依存する。公開出金先を接続コントラクトにするだけでは充足しない。期限の時刻と比較境界は接続仕様、署名・ハッシュ・ABIは設計へ引き継ぐ。

### USEC-02 支払い失敗時の一体取消

- **対応要求**: U-02、U-07。
- **区分**: 必須。
- **対象者**: 支払者と資産操作を検証する開発者。
- **前提**: 実行直前と実行後の関連資産状態、入力消費・残額生成、成功記録を比較できる。
- **要件**: 交換失敗、最低受取額未達、着金条件不成立、認可不成立、期限切れでは、当該支払いに伴う入力消費・残額生成・出金・交換・着金・成功記録を一体に取り消す。
- **受入条件**: 正常: 全条件を満たす支払いは全資産効果を確定する。異常: 各失敗で当該試行の資産効果と成功記録を残さない。交換・送付失敗を処理して出金だけを成立させる経路、外側の成功を支払い成功と誤認する経路は不合格とする。
- **検証方法**: 下表の失敗を区別した自動テストと、UTXO、本体、接続先、交換先、最終受取人の関連資産状態の前後比較。障害注入は異常系の補助として用いてよい。
- **必要な証拠**: 失敗箇所、実際に通る呼出しと失敗伝播、入力・残額・ETH・トークン・成功記録の前後差分、gas等の取消対象外の差分、期待結果と成否。
- **限界と依存**: 本体FR-04、SEC-01、SEC-05と[失敗と外部呼出し](../../specification.md#失敗と外部呼出し)に依存する。同一Ethereumトランザクションへの包含だけでは充足しない。先に確定した報酬受領、当該試行と無関係の操作、外側のgas支出・nonce等は取消対象外とする。

| 必須の失敗ケース | 個別に判定する結果 |
| --- | --- |
| 最低受取額未達 | 交換可能でも着金下限を満たさず、出金を含めて取り消す |
| 交換処理の失敗 | 交換先で処理できず、入力消費と出金を残さない |
| 最終着金の不成立 | 交換出力を得ても最終受取人に必要な全量が届かなければ取り消す |
| 認可不成立・期限切れ | 意図が無効な支払いについて資産効果と成功記録を残さない |
| 出金単独成立の試み | 後段の失敗を握り潰す呼出しや、支払いの認可から出金だけを切り出す呼出しで資産を引き出せない |

失敗後の未使用性は当該試行の効果について確認する。
別の正当な操作が入力を消費した場合まで未使用へ戻す要件ではなく、失敗後に必ず再使用できるとも保証しない。

### USEC-03 再使用と競合と再入の安全性

- **対応要求**: U-02、U-04、U-07。
- **区分**: 必須。
- **対象者**: 支払者、提出者、接続の実装者。
- **前提**: 操作と入力の同一性、採用する実経路、外部呼出しの境界を特定できる。
- **要件**: 成功済み支払いの再使用と入力の二重使用を防ぎ、競合や再入があっても無断使用、資産生成、中間状態の悪用を認めない。
- **受入条件**: 正常: 正当なコピー提出では同じ認可済み効果が一度だけ成立する。異常: 提出者、外側の取引、呼出し経路を変えても成功済み操作を再実行できない。認可検証後に別操作が入力を消費した場合は拒否する。再入を安全に拒否するか、認可された独立操作として扱い、外側の支払い失敗時には付随して受理した内側の効果も取り消す。
- **検証方法**: コピー提出、成功後の再提出、入力を共有する別の認可済み操作、検証後の競合、実装が公開する別経路からの再使用、再入の成功・失敗の自動テスト。
- **必要な証拠**: 操作とUTXOの対応、各試行の順序、受理・拒否、消費回数、関連資産と成功記録の差分。未実装経路は対象外として明示する。
- **限界と依存**: 本体SEC-01〜SEC-05、FR-09と[操作の再使用と競合](../../specification.md#操作の再使用と競合)、[出金先と再入](../../specification.md#出金先と再入)に依存する。複数の実認可方式やNative AAの実装を要求するものではない。

## 機密性の要件

### UPRIV-01 公開情報と秘密の境界

- **対応要求**: U-05、U-07。
- **区分**: 必須。
- **対象者**: 支払者、公開情報の観測者、評価者。
- **前提**: 採用方式の秘匿の根拠、本体と接続が公開するデータ、秘密の保持者を列挙できる。
- **要件**: 公開グラフ、使用ETH額、出力トークンと金額、最終受取人、所有者に関する情報、送信元、gas、認可・受領データ等の実装由来メタデータを評価に含める。非公開の秘密鍵、認可用秘密、金額秘匿に必要な秘密を公開データ・通常ログ・共有成果物へ漏らさない。
- **受入条件**: 正常: 実際の公開範囲と非公開情報、秘密の保持者、暗号の前提を説明できる。異常: 平文漏えい、公開項目の省略、所有者や送信元の秘匿を無条件に主張する説明、収支の不確定性だけを暗号的秘匿の証明とする説明は不合格とする。
- **検証方法**: 実行データ、ログ、公開手順の点検と漏えいテスト。採用方式の一次資料・版・仮定と、本体から追加された公開情報を照合する。
- **必要な証拠**: 公開・非公開情報一覧、データの出所と閲覧者、秘匿の根拠、公開成果物の点検結果。研究用に明示公開する金額と、本人向け表示・鍵を区別する。
- **限界と依存**: 本体SEC-06、PRIV-01と[公開情報と秘密の範囲](../../specification.md#公開情報と秘密の範囲)に依存する。公開履歴の消去、通信監視や端末侵入への対策は保証しない。

### UPRIV-02 報酬額と残額の推論の対照例

- **対応要求**: U-05、U-07。
- **区分**: 必須。
- **対象者**: 公開チェーン情報だけを知る第三者、取引相手の情報も知る観測者、評価者。
- **前提**: 下記の履歴、具体額、評価時点、公開・非公開情報、追加知識の出所を固定する。
- **要件**: 支払い後も報酬額と残額に複数の収支候補が残る例と、既知額または後続公開操作により一意になる例を再現する。残額再送金後と追加情報取得後を別々に評価する。
- **受入条件**: 正常: 各時点の収支条件と観測情報から候補と一意性を再計算でき、全公開情報と暗号の前提を踏まえて残る不確定性を説明できる。異常: 観測者に与えていない秘密を使う、メタデータによる絞込みを無視する、複数候補の実例を示せない場合は未達とする。
- **検証方法**: 固定した履歴の実暗号実行と、知識を段階的に追加する推論スクリプト。報酬支払元、最終受取人、情報共有後の観測者も比較する。
- **必要な証拠**: 取引グラフ、観測情報一覧、収支式、対象金額、時点別の結果、候補範囲を示せる場合はその範囲、メタデータの検討、再現手順。
- **限界と依存**: 本体PRIV-01〜PRIV-03と[推論シナリオ](../../specification.md#推論シナリオ)に依存する。全ケースの厳密な候補数は必須ではない。実例が成立しなければ理由を示し、PRDまたは方式を見直す。

### 必須の推論履歴

金額の倍率を`u`とし、正の整数weiで、`10u`が本体の金額上限内に収まるよう評価前に固定する。
実際の交換で正の出力を得られる流動性と単位を選び、換算値と選定条件を記録する。
以下は収支上の具体例であり、未選定の実装で秘匿が成立したという実測結果ではない。

報酬支払元Aが`10u`を公開入金し、支払者Bへ報酬`x`、Aへ釣銭`10u - x`を機密送金する。
Bは報酬の単一UTXOから`3u`を公開支払いし、残額`r = x - 3u`を保持する。
実行する例を`x = 6u`とし、Aの釣銭は`4u`、Bの残額は`3u`となる。
他の入出金や金額を持つ出力を加えず、gasは別の公開ETHから支払う。

| 時点・観測者 | 利用できる情報 | 対象金額について確認する結果 |
| --- | --- | --- |
| 支払い直後・公開情報のみ | 公開入金`10u`、2出力への分割、Bの入力と支払い`3u`、正の残額、UPRIV-01の全公開情報 | 収支だけでは`3u < x < 10u`。`x = 6u, r = 3u`と`x = 7u, r = 4u`がともに整合する。実装の追加情報を適用しても複数候補が残る根拠を示す |
| 残額の再送金後・公開情報のみ | Bが残額全量を別所有者Cへ機密送金した公開グラフ。Cの出力以外に金額を持つ出力はない | 収支だけではCの受領額が過去の`r`と同じと分かる。額自体の一意性は公開メタデータを含めて再評価する |
| 報酬支払元の知識を追加 | 同じ履歴に、Aが知る`x = 6u`を追加 | `r = 3u`に一意化する。公開情報のみの時点との差を示す |
| 最終受取人の知識を追加 | 最終受取人が知る受取トークン額と支払いの対応を追加 | 受取額が既に公開情報なら新しい収支条件は増えない。別の非公開知識を使う場合は明示する |
| 相手間の情報共有 | Aの報酬額と最終受取人の支払い情報を組み合わせる | 報酬・支払い・残額の対応と一意化を説明し、情報共有前の保証を維持すると主張しない |
| 後続の全額公開出金・公開情報のみ | 上記の追加知識を与えない観測者に、Cが当該出力だけを入力として残額なしで`3u`を全額出金した履歴を追加 | 再送金前の`r = 3u`、過去の`x = 3u + 3u = 6u`が判明する。過去履歴が残ることを含めて再現する |

候補額は観測者の収支推論に関する候補であり、同じコミットメントに複数の正しい開示値があるという意味ではない。
評価者が動作確認用に知る実額を、公開情報のみの観測者へ渡さない。
追試資料では試験用の既知値と観測者への入力を分け、各追試者が自分の鍵と秘匿用乱数を生成する。

## コストの要件

### UEVAL-01 操作別の費用と公開交換との比較

- **対応要求**: U-06、U-07。
- **区分**: 必須。
- **対象者**: 支払者、測定担当者、結果を読む評価者。
- **前提**: 実暗号を伴う接続と、公開ETHを同じトークンへ交換して同じ受取人へ届ける通常経路を実行できる。
- **要件**: 支払い単体の実行gasと証明生成時間を測り、通常の公開交換との差を示す。報酬受領、同期・受領確認、支払い、残額再送金の負担も下表の範囲で分けて測る。
- **受入条件**: 正常: 同じ環境、交換額、トークン、受取人、交換経路、価格条件、流動性等の初期状態で比較し、追加負担と揃えられない差を説明できる。異常: 暗号検証の省略、準備費用の隠蔽、同じ費用の二重計上、異なる条件の無説明な比較は不合格とする。
- **検証方法**: ローカルで同じ交換前状態を再現した反復実行、取引記録とオフチェーン計測の照合、公開テストネットでの実測gasの記録。
- **必要な証拠**: 操作別・経路別の測定値、公開交換との差分、資産移動条件、測定区間、初回と反復の内訳、成功と代表的失敗の結果。
- **限界と依存**: 本体FR-08、EVAL-02〜EVAL-04を参照する。公開交換に存在しない証明生成は「対象外」とし、仮想の費用を加えない。数値上限、低コスト、先行機密方式への優位性を合格条件にしない。

### UEVAL-02 測定条件と生データの再現

- **対応要求**: U-06、U-07。
- **区分**: 必須。
- **対象者**: 測定担当者と第三者の検証者。
- **前提**: 測定前に実装・環境・入力・状態・計測方法を固定できる。
- **要件**: 本体と接続のコード版、暗号・認可・証明生成器、Uniswapとトークンの版・設定、依存版、ハードウェア、EVM、RPC、入力、履歴量、初回・反復状態、反復回数、集計方法を記録し、生データと再現スクリプトを提供する。
- **受入条件**: 正常: 第三者が同じ条件で実行・集計し、変動と適用範囲を説明できる。異常: 都合のよい値だけの選別、版不明、失敗やスキップを隠す集計、公開ネットワークの異なる状態を同一条件とする比較は不合格とする。
- **検証方法**: 固定条件と実行記録の照合、生データからの再集計、初期状態の復元を含むローカル再実行。
- **必要な証拠**: 測定前の条件、全試行の値・成否、集計手順、再現コマンド、比較不能な条件と理由、公開テストネットの取引・gas記録。
- **限界と依存**: 本体EVAL-04、OPS-01〜OPS-03を参照する。反復回数、具体的ツールと統計量は評価計画で定める。異なる機器や公開ネットワークの値の完全一致は要求しない。

### 計測範囲と会計

| 区分 | 記録する範囲と内訳 |
| --- | --- |
| 報酬の送金と受領 | 報酬送金の取引全体のgas、必要な証明・認可・受領データの生成、受取側の同期・復号・整合性確認。支払い単体へ合算しない |
| 支払い単体 | 支払条件の認可生成、必要な証明生成、入力消費・残額生成・暗号検証・出金・交換・着金を含む取引全体のgas。残額の同期・受領確認は別欄にする |
| 残額再送金 | 再送金の証明・認可生成と取引全体のgas、再送金先の同期・復号・受領確認 |
| オフチェーン処理 | 証明生成、認可生成、受領データ生成、同期・復号・整合性確認の時間と資源。処理の開始・終了、履歴量、キャッシュ等の再利用、重複区間を記録する |
| 取引の内訳 | 受領データ掲載や個別検証のgasを分解する場合は取引全体の内数とし、合算時に二重計上しない |
| 初回と準備 | デプロイ、登録、セットアップ、前処理、テスト資産・流動性の準備を通常操作と分ける。再利用可能な範囲と、各反復で必要な準備を示す |
| 成功と失敗 | 成功時に加え、最低受取額未達による取消、認可改ざんまたは期限切れによる拒否の負担を測る。未送信・呼出しシミュレーションと実取引のgasを混同しない |
| 通常の公開交換 | 同じ交換と着金に必要な認可・準備・取引全体を計測し、機密報酬の受領や残額再送金とは比較単位を分ける |
| 一連の操作の集計 | 操作ごとのオンチェーン費用、オフチェーン処理、初回費用を分け、合計する場合は包含範囲を明示する。gasと時間を一つの値に足さない |

gasと支払資産は別会計とし、失敗で失われたgasをUTXOや最低受取額から補填しない。
公開テストネットの記録は実経路の動作と実測gasの証拠、ローカルの反復測定は条件を揃えた差分評価の証拠とする。

## 運用と再現性の要件

### UOPS-01 確定状態と再試行の確認

- **対応要求**: U-02、U-07。
- **区分**: 必須。
- **対象者**: CLIを使う支払者と提出者。
- **前提**: 本体の確定・同期規則と、支払いの認可内容・実行結果を照合できる。
- **要件**: 成功、失敗、未確定、通信上の確認不能を区別し、再試行前に確定履歴、対象操作、入力の未使用性、期限を再確認する。
- **受入条件**: 正常: 認可した着金と入力・残額の整合を確認した支払いのみ成功として扱う。異常: RPC通信失敗を未実行と決めつけない。入力が消費されたことだけで意図した支払いを成功としない。再編成・履歴再取得でも二重計上せず、成功済み操作を再使用しない。
- **検証方法**: 通信中断、未確定、失敗後の再確認、コピー提出、別操作の競合、再編成と再同期のCLI自動テスト。
- **必要な証拠**: CLIの状態表示、採用履歴と確認時点、支払い意図との照合、再試行の可否と根拠、入力・残額・着金の記録。
- **限界と依存**: 本体FR-07、OPS-04と[受領と同期の状態](../../specification.md#受領と同期の状態)、[操作の再使用と競合](../../specification.md#操作の再使用と競合)に従う。鍵と公開履歴へアクセスできることに依存し、必ず再試行できることや本番SLAを保証しない。

### UOPS-02 両環境での実暗号による検証

- **対応要求**: U-03、U-07。
- **区分**: 必須。
- **対象者**: 接続の開発者と検証者。
- **前提**: 本体・接続・Uniswap・トークンの対象版、実暗号経路、環境と流動性を特定できる。
- **要件**: 下記の環境別必須検証を満たし、正常経路で実際の暗号検証とテスト用資産の実移動を行う。
- **受入条件**: 正常: ローカルの正常・異常系自動テストと評価、公開テストネットの一連の操作と代表的失敗・拒否が再確認できる。異常: ダミー証明、検証省略、成功デモのモック化、公開デプロイだけ、ローカル成功のみでの代替は不合格とする。
- **検証方法**: CLIと自動テスト・評価スクリプトを固定版で実行し、公開テストネットの取引または呼出しを要件へ対応付ける。
- **必要な証拠**: 環境、版、設定、デプロイ先、Uniswapの利用箇所、トークン、流動性、実際の暗号検証経路、テストの成否、公開記録と実測gas。
- **限界と依存**: 本体OPS-01〜OPS-03を参照する。公開テストネット未確保は未達の依存とする。ローカルでforkを使うかローカルデプロイを使うかは設計に委ね、由来と版・初期状態を固定する。

### UOPS-03 第三者による追試

- **対応要求**: U-07。
- **区分**: 必須。
- **対象者**: 作成者以外の開発者と評価者。
- **前提**: 公開リポジトリ、必要なソフトウェア・資源、RPC・履歴、テスト用資産にアクセスできる。
- **要件**: 第三者が自分の鍵とテスト用資産を使い、公開手順から環境準備、正常・異常系、推論評価、コスト計測・集計を追試できる。
- **受入条件**: 正常: ソフトウェアと版、設定、資源、鍵の準備、RPC・履歴、テスト資産・流動性の準備、コマンド、期待結果、既知の制約が揃い、手順どおり再実行できる。異常: 作成者だけが持つ鍵・非公開設定、実資金、専用の受領データ配送サービスを必須にしない。
- **検証方法**: 公開手順だけを用いた第三者の実行と、期待結果・要件ID・証拠の照合。
- **必要な証拠**: 固定版の手順とスクリプト、設定項目、資産・流動性の準備条件、再実行記録、各要件の成否と未検証範囲。
- **限界と依存**: 本体OPS-03を参照する。通常のノードやRPCへの依存を明示し、テストネットや第三者サービスの永続提供は保証しない。

### UDEL-01 応募用PoCの技術的な証拠

- **対応要求**: U-03、U-07。
- **区分**: 必須。
- **対象者**: PoCの評価者と応募担当者。
- **前提**: 要件ごとの対象コード、実行結果、未達の依存を追跡できる。
- **要件**: CLIデモ、正常系、取消、認可保護、機密性の対照例、コスト比較と追試をU-01〜U-07へ対応付ける。本体全体の未完了要件と接続で得た証拠を分ける。
- **受入条件**: 正常: 各主張が実行記録へ対応し、本体の未完了の比較評価・形式証明、外部依存と信頼前提を識別できる。異常: 接続のテスト成功を本体の形式証明完了と扱う、未実行・スキップ・未判定を合格とする、未測定の優位性を主張する場合は不合格とする。
- **検証方法**: 下記対応表、デモ、コード、各証拠、後続の応募資料を照合する。U-03全体の達成判定では、Issue #9で管理する応募条件の充足確認とその根拠も照合する。
- **必要な証拠**: 要件別の成否と根拠、CLI実行手順、本体の未完了要件ID、証明済み範囲と対象版、外部のUniswap・トークン等への信頼前提、応募担当への引継ぎ。U-03全体の達成には、Issue #9の応募条件の充足確認と根拠への参照も必要とする。
- **限界と依存**: 本体FV-01〜FV-04、EVAL、OPSの要件を維持する。接続固有の形式証明は後続課題。本書作成の完了に受賞、応募資格の確定、提出完了は要求しない。

UDEL-01の技術的な証拠の合格だけでは、U-03全体を達成済みとしない。
U-03の達成には、対応する技術要件の充足に加え、[Issue #9](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/9)で管理する応募条件の充足確認を必要とする。
応募条件が未確認・未充足の場合は、技術要件の結果と区別してU-03を未達とする。応募の進捗と確認の根拠はIssue側で管理する。
