# Uniswap接続の仕様

## 目的と記載範囲

[接続PRD](PRD.md)のU-01〜U-08と[接続要件定義](requirements.md)の全20要件について、方式に依存しない支払い、公開サイト、デモ報酬要求の振る舞いを定める。
[Issue #25](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/25)の参照開始コミットと着手時のHEADは、ともに `5d9e378ed9d1e970723a198b244e74aa868d6c74` である。同Issueの範囲と、仕様策定の対話で合意した五つの判断を反映する。
用語、判断根拠、要件対応と設計への引継ぎは本書に集約する。

本書は接続の振る舞いの基準であり、本体の保証の正本は[本体仕様](../../specification.md)と[本体要件](../../requirements.md)である。
本体の状態や操作を再定義せず、組合せに必要な追加条件を定める。
仕様の完成は実装、実暗号検証、形式証明、実測、公開サイト、応募の完成を意味しない。
現行の[本体設計](../../design.md)と[アーキテクチャ](../../architecture.md)は依存の確認に使い、接続方式の採用・実証の根拠として読み替えない。

最低必須の支払いは、単一所有者の単一UTXOから固定額のETHを全額交換し、一銘柄の公開トークンを指定先へ全量渡す部分支払いである。
正の残額は支払者の機密UTXOに保持する。gasは別の公開ETHから支払う。
複数入力と残額ゼロの支払いは追加対応であり、未対応なら資産効果を残さず拒否する。追加対応も本書の認可、取消、保存、受領の保証を維持し、対応する検証を追加する。今回のPay UIは単一入力・正の残額に限定する。
本体の合算、全額出金などの対応範囲は縮小しない。

実資金を扱わない研究用PoCとし、厳密な請求額決済、交換額の秘匿、出力トークンの再秘匿、本体の多資産化、複数人の集約交換、本番運用は対象外とする。
Router・暗号方式・鍵構成等の採用は、本書の確定後に設計で行う。

## 用語と操作の同一性

対応要件: UFR-01〜UFR-03、USEC-01〜USEC-03、UOPS-01、UUI-03・UUI-06。

本体の[用語](../../specification.md#用語)と[提出と実行文脈](../../specification.md#トランザクションの提出と実行文脈)を継承する。

| 用語 | 意味と区別 |
| --- | --- |
| 支払者 | 入力UTXOの所有者として支払いを認可する利用者 |
| 提出者・ガス支払者 | 認可済み内容を提出する主体と、公開ETHでgasを支払う主体。所有者との一致を一般条件にしない |
| 公開出金先 | 本体から支払い用ETHを受け取る先。交換後の最終受取人とは別の役割 |
| 最終受取人 | 支払い完了時に交換出力全量を保有する、認可された公開トークンの宛先 |
| 報酬支払元 | 支払者へ機密ETHを送金する所有者。送った実額を知るが、受取人の使用権限を取得しない |
| 支払い | 本体の入力消費・残額生成・出金、交換、最終着金、成功記録を組み合わせる資産操作 |
| 認可済み支払い操作 | 所有者が対象環境、入力、残額、支払条件と識別情報を固定して認可した一つの意図 |
| 支払い試行 | その認可済み操作を成立させようとする一回の実行。失敗しても認可そのものが失効するとは限らない |
| 外側のトランザクション | 支払い試行を含むEthereumの取引。一つの取引に複数操作を含め得る。取引ハッシュは支払い意図の識別とは異なる |
| 最低受取額 | 認可されたトークンの実受取額の正の下限。請求額と厳密に一致させる条件ではない |
| 残額 | 入力の機密ETHから固定使用ETH額を引いた額。交換後の返金や余剰トークンを指さない |
| 交換出力全量 | 認可したETH全額の交換によって得る、認可された出力トークンの総量。最終送付時の控除前の額 |
| 実受取額 | 当該交換出力のうち、支払い完了時に最終受取人へ帰属して残っている額 |
| 資産効果の取消 | 失敗した試行に付随する資産・成功記録の巻戻し。認可の任意失効や過去の成功の取消ではない |
| 再確認 | 履歴・資産状態を読み、既存の操作・要求の状態を照合すること。送信や新たな配布を開始する操作ではない |
| 報酬受取要求 | 利用者が指定額のデモ報酬を自分宛てに求める一つの意図。オンチェーン送金操作やその実行試行とは別に識別する |

同じ認可済み支払いは、提出者、外側の取引、呼出し経路、署名・証明の表現を変えても同じ操作である。
外側のnonce更新や証明再生成だけでは新しい支払いにしない。本体の[再使用と競合](../../specification.md#操作の再使用と競合)に従い、成功済みの同じ操作を再実行しない。
支払条件、入力、残額の出力内容などの認可対象を変更する場合は、新たな認可を必要とし、元の認可を書き換えた扱いにしない。
同じ入力を使う異なる認可済み操作は競合であり、同一操作のコピー提出と区別する。

支払いの識別は本体の出金操作と対応し、接続側の識別だけを変えて同じ出金を再使用したり、異なる支払条件に付け替えたりできないものとする。
支払い一件に対応する本体出金は一件であり、同じ出金を複数の成功支払いに対応付けない。
報酬の送金、支払い、後続の残額再送金は、それぞれ独立した操作である。一連の履歴全体を一つの取消単位にはしない。
識別子、nonce、署名、ハッシュ、保存形式は設計事項とする。

## 論理状態と資産帰属

対応要件: UFR-02〜UFR-03、USEC-02〜USEC-03、UPRIV-01。

### 本体から継承する状態

本体のUTXO集合、成功済み操作の履歴、裏付けETH・債務・未計上ETHは、[論理状態と資産保存](../../specification.md#論理状態と資産保存)に従う。
接続が入力の所有者・金額を変更したり、交換で得た公開トークンを機密ETH債務として発行したりすることは認めない。
本書の数式で用いる非公開金額は論理上の値であり、平文公開を求めるものではない。

| 記号・情報 | 意味 |
| --- | --- |
| `p`、`a` | 認可済み支払い操作と、その一つの試行 |
| `i`、`o` | 支払いの入力UTXOと生成する残額UTXO |
| `V`、`w`、`r` | 入力額、固定使用ETH額、残額。整数wei |
| `T`、`R`、`m`、`d` | 認可されたトークン、最終受取人、最低受取額、有効期限 |
| `q`、`y` | 交換出力全量と実受取額。`T`の最小単位による整数 |
| `Hpay` | 成功した支払いと本体出金・入力・残額・着金を対応付ける論理的な成功履歴 |
| 観測履歴 | 対象チェーン・デプロイ、採用したブロックの識別と位置、確定条件、照合した操作・資産の記録 |

`Hpay`は論理上の履歴であり、独立したストレージやイベントの新設を指定しない。公開履歴から同じ意味を照合できることを求める。
本体の成功履歴と別々に確定させ、片方だけ成功している支払いを作らない。

### 支払い由来の資産と全量着金

一つの試行について、当該出金の`w`、その交換途中の資産と、最終出力`q`を対応付ける。
交換への一時的なラップや中間資産の表現は設計に委ねるが、`w`の全額が認可された交換へ投入され、途中の返金・残留がないことを必要とする。
中間資産を支払者への公開返金として残すことや、接続先の既存資産を不足分に充当することで全額交換と扱うことは認めない。
交換そのものの対価やプール内の手数料は、採用経路で得られる`q`を決める交換条件として記録する。`q`を得た後で送付手数料などを控除し、少なくなった額を「交換出力全量」と呼び直さない。

完了境界は、出金・交換・最終送付とそれに伴う呼出しを終え、当該支払いの成功を確定させる時点とする。
この境界で `y = q ≥ m > 0` とし、最終受取人に全量が残ることを求める。
同じ支払い処理中に受取人が資産を別の宛先へ転送し、全量が残らなければ失敗とする。完了した後の別操作による使用・転送は制限しない。
同じ外側の取引内に後続の独立操作がある場合も、支払いの完了境界と後続操作を区別する。取引全体の前後差だけでこの境界を置き換えない。

次の情報を着金の代用にしない。

- 最終受取人や接続先が支払い前から持つ残高、無関係な送金、第三者の補填。
- 交換処理や送付処理の戻り値、イベント、外側の取引の成功だけによる申告。
- 別トークンの入金、別受取人への送付、中間先での保有。

具体的な残高照合・資産移動の検証方法と、トークンの手数料・残高変動・コールバック等への対応は設計で固定する。
単純な残高差を使う場合も、無関係な増減が混ざらない根拠を示す。資産の帰属を検証できない経路を適合としない。
通常アドレスとコントラクトという分類だけで受理を決めず、指定先へこの着金条件を成立させられることを必要とする。満たせない受取先・トークン・経路は未対応として拒否する。

### 成功と失敗の資産状態

本体の[基本操作](../../specification.md#基本操作)と[ガス会計](../../specification.md#ガスと資産移動の会計)を継承する。
次表は当該支払いによる効果であり、無関係な操作による変化を含めない。

| 状態・資産 | 成功時の効果 | 試行失敗時の効果 |
| --- | --- | --- |
| 入力・残額 | `i`を一度消費し、支払者所有の`o`を額`r`で一つ生成 | 当該試行による消費・生成なし |
| 本体の債務・裏付け | ともに`w`減少。`V = w + r` | 当該試行による減少なし |
| 未計上ETH・無関係UTXO | 支払いの原資に使わず、当該支払いで変更しない | 当該試行による変更なし |
| 公開出金先・中間先 | 当該`w`を交換へ渡し、当該試行由来の未使用ETH・中間資産・出力トークンを残さない | 当該試行に付随する残高・資産移動を巻き戻す |
| 交換先 | `w`の全額に対応する交換が成立し、出力は`T`の`q` | 当該交換による資産・交換状態の変化を巻き戻す |
| 最終受取人 | 当該支払い由来の`T`を`y = q ≥ m`保有 | 当該試行による着金なし |
| 成功履歴 | 本体出金と`p`の成功が対応し、`Hpay`に一度だけ加わる | 本体・接続に成功記録を残さない |
| gas・外側nonce | 外側の取引規則に従う | 外側の取引規則に従い、資産効果の取消とは別に記録 |

この会計は取引全体の資産残高が常にこの差分になるとの主張ではない。独立操作、gas、後続の資産使用を分けたうえで照合する。
失敗前に別の正当な操作が入力を消費していた場合、その消費を巻き戻さず、失敗後の入力未使用性を保証しない。

## 受理条件と認可

対応要件: UFR-02、USEC-01〜USEC-03。

### 金額と入力の境界

最低必須経路は `0 < w < V`、`r = V - w > 0` を満たす。
ETH額・UTXO額の単位と上限は[本体の金額と入出力数](../../specification.md#金額と入出力数)を継承し、各値を範囲内の整数として検証する。
入力は存在し、未使用で、支払者に属する一つのUTXOとする。残額も同じ所有者へ生成し、本体の受領データとの対応を満たす。
最小の正の残額は1 weiとする。交換の実行可能性と、正の交換出力が得られることは別の受理条件である。
`w = 0`、負値、精度超過、`w ≥ V`、不存在・消費済み入力、未対応の複数入力は最低必須経路で拒否する。

最低受取額`m`は`T`の最小単位による正の整数とする。最小値は1単位、ゼロ・負値・端数・対応する表現範囲外は拒否する。
トークンの識別、最小単位、表示換算、有限表現の上限は設計で固定し、上限ちょうどは表現上受理可能、上限超過は拒否とする。これらの範囲検査を通っても、交換・着金条件を満たさなければ支払いは成立しない。
値を黙って丸めたり、別の宛先・トークンへ補正したりしない。
`y = m` は着金条件を満たす。`y < m`は拒否し、`y > m`でも超過分を含む`q`全量を同じ受取人へ渡す。

### 認可対象と実行時の検査

本体の[認可対象](../../specification.md#認可対象)および[認可結果の検証](../../specification.md#認可結果の検証)に、接続の五条件 `w, T, m, R, d` を結合する。
チェーン・本体と接続のデプロイ・適用規則、操作の識別、本体出金の入力・残額・所有者・受領データ・公開出金先との対応を保ち、同じ認可を別の支払いへ読み替えられないことを必要とする。
未知の規則、環境や版の不一致は拒否する。秘密金額を平文で公開する指定ではない。

| 段階 | 必要な検査 |
| --- | --- |
| 準備 | 入力と受領の使用可能性、金額形式と範囲、対応環境・トークン・受取先、見積りとgas等の準備を確認する。ここでの成功は実行の保証ではない |
| 認可 | 所有者が確認した内容を固定し、本体出金と五条件の対応を検証できる認可を得る |
| 実行 | 認可の真正性と対象結合、本体の全受理条件、現在の入力未使用性、成功済みでないこと、期限を再検査する |
| 完了 | 全額交換、`y = q ≥ m`、正しい残額、本体と接続の成功記録の対応、中間残留なしを確認し、全効果を一体に確定する |

いずれかを満たさなければ拒否し、途中で満たせなくなった場合は試行全体の効果を取り消す。
条件がすべて成立し、対応経路・流動性と必要な実行資源がある正当な支払いは成功しなければならない。全件拒否を安全性の達成とはしない。
別の提出者による同じ認可済み内容の提出は、当該経路の条件を満たせば受理可能とする。提出者に条件の変更権限を与えない。

公開出金先を接続コントラクトにするだけでは、交換条件との結合を満たさない。
認可を偽装する、五条件の一つを変える、出金や入力・残額を付け替える、別チェーン・別デプロイへ流用する、出金だけを切り出す経路では資産を引き出せないものとする。
提出者の成功フラグや、先行する認可検証の成功だけを実行時の検査に代用しない。

### 有効期限

実行されるブロックのタイムスタンプを`τ`、認可された期限を`d`とし、`τ ≤ d`を受理条件とする。
`τ = d`は期限内、`τ > d`は期限切れである。期限は当該チェーンのブロック時刻と比較可能な整数秒で表す。具体的な符号化と表現上限は設計で固定し、不正形式・負値・上限超過を拒否する。
有限の期限を必須とし、省略値を無期限の認可として扱わない。
資産効果を成立させる実行で判定し、事前検証、署名時刻、送信時刻、端末時計だけでは代替しない。
期限内の事前検証後に期限を超えた実行は拒否する。

期限内に実行された支払いは、確定条件を満たすまでの間に期限を過ぎても、そのことだけで取り消さない。
再編成後の新たな実行は、その実行ブロックの時刻で判定し直す。
UIによる期限切れ判定もチェーン時刻を確認する。期限切れだけで過去の実行がなかったとは判断せず、履歴・入力状態を照合する。
自動設定する有効期間は設計事項であり、利用者へ実際の期限を提示して認可する。

## 状態遷移と一体取消

対応要件: UFR-01〜UFR-03、USEC-01〜USEC-03。

### 正常経路と不変条件

1. 支払者が報酬の確定出力を発見・復号し、整合性、所有権、未使用を確認する。これは本体の[受領保証](../../specification.md#受領の保証と不整合な受領データ)に従い、送信者の追加協力を要求しない。
2. 認可した支払いを実行し、入力消費、残額生成、出金、交換、全量着金、成功記録を一体に確定する。
3. 支払者は支払いの確定と残額の受領・未使用をそれぞれ照合し、確認できた残額だけを利用可能へ計上する。
4. 残額を別所有者へ機密再送金し、その所有者が受領と使用可能性を確認する。後続の独立操作として検証し、支払い自体の取消単位へ含めない。

全遷移で、入力の一度だけの消費、`V = w + r`、出力の正当な所有と受領対応、五条件の認可、全量交換・着金、成功記録と資産の一致を保つ。
これらはローカル表示上の手順だけでなく、実経路が満たす条件である。

### 失敗の伝播

本体の[確定と取消](../../specification.md#確定と取消の単位)と[外部接続](../../specification.md#複数操作と外部接続)に対し、接続は交換・着金まで取消単位を広げる。
失敗が起きた箇所にかかわらず、当該試行の入力消費・残額生成・出金・交換・着金・成功記録を残さない。

| 失敗 | 判定と必要な結果 |
| --- | --- |
| 認可不成立・期限切れ | 無効な支払いを拒否。先行検証済みでも実行を成立させない |
| 交換失敗 | 入力消費と出金を含め取消。交換先だけの取消で済ませない |
| 最低受取額未達 | 出力が得られても、着金下限に届かなければ支払い全体を取消 |
| 着金不成立 | 一部送付、別宛先・別トークン、受取先での即時転送、中間残留も含め取消 |
| 出金単独成立の試み | 後段を呼ばない、別の支払いへ流用する、後段失敗を握り潰す場合も出金を確定させない |
| 実行資源不足・外部呼出し失敗 | 正しい認可があっても、完了できなければ当該試行の全効果を取消 |

同じEthereum取引に含まれることだけを原子性の根拠にしない。
設計では呼出しと失敗伝播を資産状態に対応付け、必要な巻戻しが起きることを実際の経路で確認する。
外側が失敗を処理して成功した場合でも、内部の支払いは失敗のままであり、その資産効果を残さない。
先に確定した報酬受領、無関係の操作、外側gas・nonceは取消対象外とする。独立操作まで一体取消することは接続の保証に含めないが、外側取引全体の失敗でともに取り消される場合は、その実結果を記録する。

### コピー提出・競合・再入

同じ支払いのコピーが複数提出された場合、成功は一度だけとする。先に成功した記録を他の試行の結果と照合し、拒否されたコピーを新しい支払いの失敗と混同しない。
入力を共有する別の認可済み操作が先に成功した場合は、入力を失った支払いを拒否し、別操作による消費を当該支払いの成功にしない。
認可確認から実際の消費までの間に競合が生じても、実行時の状態を再確認する。

[本体の再入規則](../../specification.md#出金先と再入)に従い、再入は安全に拒否するか、独立した正当な認可操作として受理する。
受理する場合は、内側にも認可・保存・再使用防止を適用し、暫定残高や未完了の成功状態を悪用させない。
外側の支払いが失敗した場合は、それに伴って受理した内側操作とその外部資産移動・成功記録も取り消す。
内側の失敗を外部先が処理し、外側が全条件を満たして完了した場合は、内側失敗だけを理由に外側を失敗と決めない。
現行本体設計の再入拒否はこの許容範囲の一つであり、接続仕様が新たに再入の受理を要求するものではない。

## 確定・受領・同期と再試行

対応要件: UFR-01・UFR-03、UOPS-01、UUI-04〜UUI-06。

### 実行結果と観測状態

チェーン上の実行結果、確定条件の充足、本人による残額の受領確認を分ける。
本体の[受領と同期](../../specification.md#受領と同期の状態)を継承し、対象チェーン・デプロイ、採用ブロック、確定条件、確認時点を記録する。
ネットワークごとの条件・設定値・根拠は設計と実行手順に固定し、未確定を利用可能資産として扱わない。

| 観測状態 | 必要な根拠 | 表示と次に許す操作 |
| --- | --- | --- |
| 未確定 | 提出済みまたは採用履歴にあるが確定条件未充足 | 待機・再確認。入力を別の支払いへ自動再使用せず、残額を利用可能にしない |
| 確定した支払い成功 | 認可した`p`と本体出金、入力消費、残額生成、`T,R,q,y`、成功履歴を確定履歴で照合 | 支払い成功を表示。残額は受領確認へ進む |
| 残額受領成立・未使用 | 確定した残額と復号内容、所有権、金額、未使用が一致 | 一度だけ残高へ計上し、後続操作に使用可能 |
| 確定した試行失敗 | 対象試行が失敗した根拠と取消後の状態を確定履歴で確認 | 試行失敗とgasを表示。他の試行と入力・期限を照合してから再試行を判断 |
| 競合で消費済み | 入力を消費した別操作を照合できる | 当該支払いの成功とせず、同じ入力での再試行を禁止 |
| 復号不能・受領不整合 | 出力は存在するが本人の受領確認が成立しない | 利用可能残高に含めず、再同期・受領確認へ。チェーン上の成功を後から取消扱いにしない |
| 確認不能 | 必要な履歴や資産状態を取得・照合できない | 成功・失敗・未実行と断定せず再確認。過去の表示は確認時点と未更新を明示 |

入力消費だけ、外側の成功だけ、Explorerリンクだけでは成功判定に足りない。
着金を含む対象操作の証拠を得られなければ確認不能とする。
支払い後に正当に使用した残額は消費済みとして扱い、過去の支払い成功と現在の残額未使用性を混同しない。

### 通信中断と再編成

送信後の応答喪失では取引ハッシュがなくても未実行と仮定せず、元の認可済み操作と履歴を照合する。
画面再読み込み・タブ切替・ウォレットやネットワークの切替で、元の操作の環境と識別を失わない。新しい接続先の操作と混同しない。
履歴へのアクセスが回復したら本体の鍵と公開履歴からUTXO状態を復元し、生成と消費を対応付ける。履歴の再取得は再配布・再送信ではなく、同じ出力を重複計上しない。

再編成を検出した場合は、取り消された履歴に基づく成功・失敗、生成・消費、確定判定を見直す。
残額の生成が取り消されたら利用可能から外し、入力の消費が取り消されても、新しい採用履歴を照合するまで再使用可能と断定しない。
再編成後の入力が未使用でも、元の支払いが未確定・確認不能なら待機する。支払い・残額・再送金の各履歴を同じ採用履歴へ揃える。
これは再編成が起きない保証ではなく、検出時の修正規則である。

### 再試行と条件変更

同条件の再試行は、試行の失敗が確定し、同じ操作の別試行が成功済み・未確定・確認不能ではなく、入力未使用、認可有効、期限内と確認できた場合に限りUIから開始できる。
未送信と確認できる準備失敗・承認拒否は、チェーン上の試行失敗とは分けて入力・準備へ戻す。
認可署名を取得した後に取引承認を拒否した場合も、未送信を確認でき、他の試行の成功・未確定・確認不能がなく、入力未使用・認可有効・期限内と確認できれば、同じ認可済み操作の初回送信を再開できる。この再開にはチェーン上の試行失敗の確定を要求しない。
再開時も準備条件と実行時の受理条件を確認し、送信有無が不明なら再確認へ戻す。条件を変更する場合は、後述の旧認可の実行不能を確認する規則に従う。
一つの失敗記録だけでは他の試行の成功や実行可能性を否定しない。
再試行時にも全受理条件を検査し、成功は保証しない。条件が変わらない既存認可を再利用できるか、その具体形式は設計に従う。

今回のUIでは、古い認可が実行可能な間は、同じ入力を使う条件変更後の支払いを開始しない。
元の認可の期限切れなど実行不能を確認し、期限内の別試行の成功がないことと現在の入力未使用性を照合してから新たな認可へ進む。
端末時計で期限を超えたことや、一つの試行が失敗したことだけでは足りない。
この条件はUIの開始制御であり、本体仕様が扱う正当な競合操作の存在を禁止するものではない。

画面での中断、条件変更、新しい認可の作成では古い認可は失効しないことを表示する。
認可を即時失効させる機能は今回追加しない。失敗時の資産効果の取消と認可そのものの失効を区別する。
確認不能時には同じ資産の再使用や新しい報酬配布を開始せず、再確認を提供する。

## 公開サイトの振る舞い

対応要件: UUI-01〜UUI-02、UUI-04〜UUI-06、UOPS-01。報酬固有の規則は次節で定める。

### 入口と共通表示

紹介ページとアプリは英語で提供する。ウォレット未接続でも、利用価値、仕組み、公開情報と機密性の限界、対象版のコード・検証結果への案内を読める。
アプリの中央カードは「Demo reward / Pay / Deposit / Withdraw」の切替式とし、初回はDemo rewardへ案内する。
Depositは別の選択肢として案内する。今回の対象外機能を未提供のまま表示する場合は「Coming soon」とし、認可・取引の開始操作を提供しない。必須機能をこの表示だけで提供済みとは扱わない。
全履歴の一覧画面は「Coming soon」とする。残額再送金UIは今回の必須範囲に含めない。残高再同期と進行中操作の再確認は必須とする。

| 共通表示 | 意味と規則 |
| --- | --- |
| ウォレットとネットワーク | 現在の接続先を示す。過去・進行中の操作にはその操作が属する接続先を保持する |
| 公開ETH残高 | 公開資産を示す。gas用資産を機密残高や支払いの残額へ混ぜない |
| 機密UTXO残高 | 本人の鍵と履歴から確認した利用可能資産を示す。未確定・受領不整合の出力を加算しない |
| 進行中操作と直近の結果 | タブ移動で失わず、再読み込み後も元の操作を照合できる |
| Explorerへの導線 | 送信済み取引のハッシュが取得でき次第「View on explorer」を表示する。該当チェーンの当該取引へ遷移する |

Explorerリンクは入金、報酬配布、支払い、出金について、未確定時と確定後の成功・失敗時に提供する。ハッシュのない操作には作らない。
リンク先の外側取引の成功だけでは、支払いの全量着金や本人の受領確認を完了としない。
公開残高・使用ETH額・公開宛先と、本人向けの機密残高・受領額を区別する。

### 準備、入金、残高再利用、出金

| 操作 | 正しい振る舞い |
| --- | --- |
| 初回準備 | 接続、対応ネットワークへの切替、外部faucetでのテストETH取得、機密資産用の鍵の準備へ案内する。不足する条件を識別し、満たすまで送信しない |
| Deposit | 入金額とgasを区別して確認する。入金確定後も本人の受領確認が済むまで利用可能残高へ加算しない |
| 別ブラウザでの再利用 | 同じウォレットと必要な本人の操作により、追加の機密鍵ファイルの移送や元ブラウザの保存情報の共有を前提とせず、公開履歴から受領・消費済み状態を再確認して使用できる |
| 再同期 | 本体の受領・同期規則に従い、同じ出力を重複計上せず、消費済み入力を利用可能に戻さない |
| Withdraw | 対象UTXOの識別と金額を表示し、選択したUTXOの全額を自分の接続ウォレットへ公開ETHで出金する |

初回利用者の準備・入金は運営者への個別依頼やCLI操作を必須にしない。ウォレットの秘密鍵をサイトに入力させない。
ウォレット接続だけで復号できるとはみなさず、必要な本人の操作を案内する。ウォレット鍵自体を失った場合の救済はここでは要求しない。
Withdrawの認可前には出金額が公開され、過去の報酬額や残額の推論につながり得ることを説明する。部分出金UIは提供対象外であり、本体の部分出金規則は変更しない。

### Payの入力と認可開始

支払額と宛先の初期値は空欄とする。「自分のアドレスを使う」は接続中ウォレットのアドレスを入力する操作であり、実際の宛先を確認する段階を省略しない。
単一UTXOの候補は、本人が使用可能と確認したもののうち `0 < w < V` を満たすものとする。自動選択した対象を詳細に表示する。
合計残高だけが足りる場合、残額がゼロになる場合、対象が使用可能と確認できない場合は送信を開始せず、その理由を示す。複数UTXOをまとめる支払いUIは「Coming soon」とする。
最低受取額と有効期限は自動設定し、詳細で確認・変更できる。最低受取額は対象トークンの最小単位による正の整数とし、ゼロを拒否する。
金額の不正形式・精度超過・範囲外、宛先の不正形式・未対応条件、gas不足、見積り未取得・失効を区別して表示し、修正・資産準備・再取得へ案内する。黙った丸めや宛先補正は行わない。
額・宛先など交換条件が変わったら見積りを再取得する。取得不能・古い見積りを実行可能と表示しない。

見積りの基準時点から判定時点までの経過量を`age`、許容する最大経過量を`maxAge`とする。両者を同じ時計・単位で比較し、`maxAge`は有限の非負値とする。
鮮度の条件は `0 ≤ age ≤ maxAge` とし、許容幅と一致する見積りも鮮度の条件を満たす。`age > maxAge`は失効、経過量が負になる場合や基準時点・経過量を確認できない場合は判定不能として、いずれも認可を開始せず再取得・再確認へ案内する。
認可開始時に鮮度を判定し、見積りの対象条件が現在の入力と一致することも確認する。鮮度の条件だけでは、他の準備・認可・実行条件を満たしたことにはならない。
基準時点の取得方法、時計・単位、`maxAge`の具体値は設計で固定する。保存済み見積りの再表示や再読み込みだけで基準時点を更新し、鮮度を回復した扱いにしない。
この鮮度判定は支払いの有効期限とは別のUI条件であり、認可開始後の鮮度変化を理由に認可済み条件を書き換えない。

| 段階 | 条件の扱い |
| --- | --- |
| 入力完了 | 使用ETH額、交換先トークン、最低受取額、最終受取人、有効期限、選択入力を確認できる |
| 「送る」の押下 | 通常経路はアプリ内の1回の開始操作で、必要なウォレット承認へ順に進む |
| 認可前の見積り更新 | 認可条件が変わったら差分を表示し、再度「送る」が押されるまで認可へ進まない |
| 認可開始後 | 確認した条件を固定する。見積り更新や接続切替で別条件へ差し替えない |
| 認可済み条件の変更 | 古い認可が実行可能な間、同じ入力を使う変更後の支払いをUIから開始しない |

入力編集や画面上の中断は認可の取消ではないと表示する。認可を即時に失効させる機能は今回追加しない。
条件変更後の再認可は、旧認可の期限切れ等による実行不能と、旧試行の履歴・入力使用状態を確認してから行う。期限切れだけで過去の成功がなかったと判断しない。
同じ条件の再試行は、対象試行の失敗が確定し、他の試行の成功・未確定・確認不能がなく、入力未使用かつ期限内と確認できる場合に限る。
未送信と確認できる操作の初回送信の再開は、この再試行と区別し、[再試行と条件変更](#再試行と条件変更)の再開条件に従う。

### 共通の操作状態

| 状態 | 表示と許される操作 |
| --- | --- |
| 準備不足・入力不備 | 不足と修正先を示す。送信を開始しない |
| 準備中 | 見積り・証明等の準備を示し、同じ開始操作を重複させない |
| ウォレット承認待ち | 承認の目的を示す。拒否後、未送信と確認できれば入力へ戻し、初回送信の再開条件を満たせば同条件で再開できる。送信済みなら結果を追跡し、送信有無不明なら再確認する |
| 送信中・未確定 | 送信・確定待ちを示す。生成予定のUTXOを利用可能にせず、同じ入力を再使用しない |
| 操作成功・受領確認中 | 資産操作の確定した成功を示す。本人の出力は復号・整合性・未使用確認が済むまで利用可能にしない |
| 成功・受領確認済み | 実着金・公開出金と本人の利用可能残高を操作に応じて示す。報酬受領後はPay、支払い後は残額確認へ案内する |
| 確定した失敗 | 試行の失敗理由、確認できた資産状態、gasを区別する。他試行・入力・期限の照合前に再試行へ進めない |
| 確認不能 | 「状態を再確認」を提供し、成功・失敗・未実行と断定しない。同じ資産の再使用と新しい報酬配布を開始しない |
| 受領の復号不能・不整合 | 利用可能残高に含めず、受領確認の問題として再同期へ案内する。これを根拠にチェーン上の出力を消費済みとしない |

再確認は履歴・元の操作・入力使用状態・期限の照合であり、新たな送信ではない。成功済みなら結果へ、未確定なら待機へ、再試行可能と判定できた場合だけ入力・認可へ戻す。
再編成では以前の判定を確定条件に照らして見直し、確認できない残高を使用可能のまま扱わない。古い残高を表示する場合は確認時点と未更新を明示する。
ウォレット・ネットワーク切替後は新しい接続先の残高・結果と元の操作を混同しない。古い接続先向けの未送信条件で認可を開始しない。
アプリの開始クリック、認可署名、取引承認は別々の操作として記録する。必要なウォレット承認が1回で済むとは表示しない。

## デモ報酬要求

対応要件: UUI-03、UUI-06、UFR-01、UPRIV-01〜UPRIV-02。
デモ報酬は、配布元から利用者への本体の機密送金である。公開gasの配布や画面上だけの残高加算では代替しない。

### 入力と要求の同一性

報酬額の初期値は空欄とし、自由入力を受け付ける。正の金額、本体の金額単位・上限、配布元の利用可能資金を条件とし、デモ専用の固定額・上下限は設けない。
不正形式、ゼロ、負額、本体上限超過、資金不足を区別して示し、修正できるようにする。受付後に実行時の資金不足が生じても成功と扱わない。

| 項目 | 意味 |
| --- | --- |
| 報酬受取要求 | 利用者が、指定した金額を自分宛てに一度受け取ろうとする意図 |
| 要求主体 | その要求を開始し、自分の受取先への配布を求めた利用者 |
| 要求額・受取先 | 受付後は固定する配布内容。本人以外の要求へ付け替えない |
| 配布試行 | 一つの要求を成立させるための送信・実行。要求に対して複数の失敗試行があっても配布成功は一度だけとする |
| 配布成立 | 当該要求に対応する機密送金が、本体の確定条件を満たしたこと |
| 受領完了 | 配布成立に加え、本人が鍵と公開履歴から受領額・整合性・使用可能性を確認したこと |
| 配布なしの終了 | 配布されておらず、旧要求に属する試行が後から成功する余地もないと確認した状態 |

同じ要求の再送と独立した要求を区別する。要求額や受取先が等しいだけでは同一要求としない。
同じ要求の再送で受付済みの額・受取先を変更した場合は、既存要求を変更せず拒否する。再送時に新しい要求へ自動変換しない。
画面の再読み込み、タブ移動、送信後の応答喪失によって要求の同一性を失わず、元の要求と配布試行を再確認できるようにする。
要求の識別・保持の表現は設計で固定するが、保存済み識別子を持たないことを、新しい配布を始めてよい根拠にしてはならない。

### 要求の状態と遷移

要求受付、配布取引の送信、配布成立、受領完了を別々の事実として扱う。試行の失敗だけでは要求の終了とみなさない。

| 要求の状態 | 判定条件 | 次に行うこと |
| --- | --- | --- |
| 入力中・未受付 | 要求の受付がまだ成立していないと確認できる | 額を修正できる。条件を満たす場合に受付へ進む |
| 受付済み | 要求内容が固定され、元の要求を識別できる | 同じ要求に対応する配布処理を進める。並行した再送は元の処理・結果へ対応付ける |
| 配布中・未確定 | 配布の準備・送信・確定待ちが進行している | 元の要求と試行を追跡する。新たな配布を開始しない |
| 配布成立・受領確認中 | 配布は確定しているが本人の使用可能性確認が未完了 | 本人の受領確認へ進む。再配布しない |
| 受領完了 | 本人の受領確認が完了している | Payへ進める。本人の明示操作による独立した追加要求を認める |
| 試行の失敗確定・照合中 | ある試行が失敗したが、要求全体の配布有無は照合中 | 他試行と資産状態を照合する。別試行が成功済みなら受領確認へ戻す |
| 再試行可能 | 配布がなく、旧試行が後から成功せず、同一要求の配布を安全に開始できる | 固定済みの要求内容で再試行できる |
| 配布なしの終了 | 当該要求による配布がなく、今後も旧試行から成立しないと確認できる | 修正した内容を新しい要求として開始できる |
| 確認不能 | 受付、送信、確定または他試行の状態を確認できない | 元の要求を再確認する。未受付・失敗と断定せず、新たな配布を開始しない |

受付の応答が失われた場合も確認不能として元の要求を照合する。取引ハッシュが未取得でも、配布が未送信だとは断定しない。
配布が成立したのに受領の復号・整合性確認が失敗した場合は、受領確認の問題として扱い、要求を未配布へ戻さない。
再編成等で配布の確定が失われた場合は、元の要求の履歴と資産状態を再照合し、二重配布を起こす再試行をしない。

### 重複、修正、追加要求

| 操作・事象 | 結果 |
| --- | --- |
| 同じ要求の連打・並行送信 | 元の要求を確認し、成功する配布を一度に制限する |
| 同じ要求の再送 | 既存の受付・試行・結果を返すか照合を続ける。再送ごとに独立した配布操作を作らない |
| 成功後の同じ要求の再送 | 成功した配布と受領確認へ戻す。再配布しない |
| 未確定・確認不能の間の額修正 | 元の要求を書き換えず、新しい配布も開始しない |
| ある試行の失敗後の修正 | その失敗だけでは新要求を開始しない。配布なしの終了を確認してから修正した新要求を開始する |
| 同じ内容での再試行 | 全試行と資産状態を照合し、旧試行との重複成功を排除した上で、元の要求の試行として行う |
| 受領後の独立した同額要求 | 本人が明示的に開始した別要求として受け付ける。以前と同額であることを拒否理由にしない |
| 別利用者からの要求照会 | 他人の要求内容や金額を返さない |

追加要求に1人1回や日次の配布上限を設けない。同一要求の重複防止を、独立した追加要求の禁止へ置き換えない。
接続ウォレットの切替は旧要求の受取先変更ではない。旧要求は元の利用者・ネットワークに所属し、新しい接続先へ配布結果や秘密情報を付け替えない。

### 公開範囲と本人の受領

紹介ページと報酬受領の入口では、公開額の単一Depositからの支払いでは差額が推論できる場合と、機密報酬からの支払いで公開情報に複数候補が残る例を区別する。
配布元は実額を知ることを説明する。本人向け表示、入力額を処理する配布元、公開情報のみを見る第三者を別の観測者として扱う。
入力額を公開API、通常ログ、共有成果物から第三者が取得できる構成を認めない。要求照会の権限もこの境界を維持する。
要求の成否、配布元残高の照会、配布規則などが公開する情報を推論評価から除外しない。自由入力の全履歴で複数候補が残るとは主張しない。
利用者の認可・受領の秘密を配布元へ渡すことを必須にしない。配布成立後は、配布元の追加協力なしに本人の鍵と公開履歴から受領を確認し、支払いに使用できる。

公開履歴の消去、通信監視や端末侵入への対策は今回の保証に含めない。
暗号的な秘匿は採用方式の一次資料、対象版と仮定に依存する。収支だけで複数候補があることを、その暗号的な証拠に代用しない。

### 必須の推論履歴

[要件定義の必須履歴](requirements.md#必須の推論履歴)を次の記号で照合する。
`u`は正の整数weiで、`10u`が本体上限内に収まり、実交換で正の出力を得られる倍率として評価前に固定する。
本体仕様で一つのUTXOを表す記号`u`とは異なり、この節だけで金額倍率を表す。
報酬支払元A、支払者B、残額再送金先C、公開トークンの最終受取人を区別する。

Aが`10u`を公開入金し、Bへの報酬`x`とAへの釣銭`10u - x`へ分割する。
Bは報酬の単一入力から`3u`を支払い、`r = x - 3u`を保持する。
実行する例は`x = 6u`、釣銭`4u`、残額`3u`とする。他の金額を持つ出力や入出金を混ぜず、gasは別の公開ETHで支払う。

| 時点・観測者 | 追加する情報 | 収支からの結論と検証義務 |
| --- | --- | --- |
| 支払い後・公開第三者 | 公開入金`10u`、分割の2出力、支払い`3u`と正の残額 | `3u < x < 10u`。`x=6u,r=3u`と`x=7u,r=4u`はともに収支整合。全公開メタデータを加えても複数候補が残る根拠を実装後に示す |
| 残額再送金後・公開第三者 | Bが`r`全量をCの単一出力へ機密送金 | Cの額は過去の`r`と等しい。全量移動だけでは収支上の新しい数値は得られない。追加メタデータを含め再評価する |
| 報酬支払元の知識 | Aが知る`x=6u` | `r=3u`に一意化。Aに対して報酬・残額の秘匿を主張しない |
| 最終受取人の知識 | 受取トークン額と支払いの対応 | すでに公開の情報なら新たな収支制約は増えない。非公開の追加知識を使う場合は出所を記録する |
| 相手間の共有 | Aの報酬額と最終受取人の支払い情報 | 報酬と支払いの対応を結び、残額が判明する。共有前と同じ保証を主張しない |
| 後続全額出金・公開第三者 | 上の秘密を与えず、Cの当該出力だけから残額なしの`3u`出金を追加 | 過去の`r=3u`、`x=6u`が一意に決まる |
| 直接Depositの対照 | Bが既知額`V`を単一UTXOへ入金し、そこから`w`を支払う | `r=V-w`が判明。Depositすれば常に額が分からなくなるとは説明しない |

候補は観測者の知識に対する候補であり、一つのコミットメントに複数の正しい開示値があるという意味ではない。
評価者が知る試験用の実額と、公開第三者に与える入力を分ける。第三者は自分の鍵・乱数で追試できるものとする。
自由入力で作られるすべての履歴に複数候補が残ること、全ケースの厳密な候補数計算は要求しない。
必須の実例に複数候補が残らない場合はUPRIV-02未達とし、方式またはPRDの見直しを行う。表示だけを隠して合格とはしない。

### 後続検証の対象となる環境

[環境ごとの必須検証](requirements.md#環境ごとの必須検証)を維持する。
ローカルではS-01〜S-50の該当分岐を正常・異常系の自動検証、推論評価と対応付ける。未対応の任意経路は拒否を確認し、再入受理等の適用不能分岐には理由を残す。
公開テストネットでは報酬受領、部分支払い、全量着金、残額再送金と受領、最低額未達の取消、認可改ざん・期限切れの拒否を必須とする。
公開サイトの初回準備、Deposit、報酬、Pay、Withdraw、別ブラウザ、Explorerも公開テストネットで確認する。制御が必要な異常系はローカルで再現する。
失敗の呼出しシミュレーションを使う場合は対象ブロック・入力・結果を固定し、実取引の取消やgasとは区別する。

### 検証の境界

本体の[証明義務](../../specification.md#証明義務と検証の境界)とFV-01〜FV-04は維持する。
接続の自動テスト、抽象モデルの確認、本体実コード・検証器の形式証明、暗号方式の安全性の根拠は異なる証拠である。
接続固有の形式証明は今回追加しない。本体の未証明・未実装を接続の成功デモで充足したと扱わない。
Uniswap、トークン、EVM、RPC、配布機能、配信コードなど実経路の信頼前提と対象版を記録する。
実暗号の検証や資産移動をモックで置き換えた正常経路を必須成果の達成としない。障害注入は異常系の補助として区別する。

後続の検証記録は、要件ID、本書の規則・シナリオ、コード版、環境・配置先、入力・初期状態、操作・試行、実結果、資産と成功記録の差分、成否と未検証範囲を対応付ける。
本書の期待結果と実行済み結果を混同せず、未実行・スキップ・タイムアウト・未判定・未達を合格にしない。

### コストと操作回数の対応

計測条件・手順は[コスト要件](requirements.md#コストの要件)と[操作回数の評価条件](requirements.md#操作回数の評価条件)を正本とし、本書では測定単位を対応付ける。

| 単位 | 本書の操作・状態との対応 |
| --- | --- |
| 支払い単体 | 認可生成・証明生成、入力消費から全量着金までを含む取引全体。残額の同期・受領確認は別欄 |
| 報酬・残額再送金 | それぞれ独立した本体送金と受領確認。支払い単体へ無条件に合算しない |
| 失敗 | 最低額未達の取消と認可改ざんまたは期限切れの拒否。未送信、シミュレーション、実取引を区別 |
| オンチェーン・オフチェーン | gas、証明・認可・配送生成、同期・復号を分け、包含関係と重複区間を明示 |
| 通常の公開交換 | 同じ環境・額・トークン・宛先・交換経路・価格と流動性の初期条件で比較。存在しない証明生成は対象外 |
| 初回と反復 | 配置・登録・準備・鍵・流動性等を別枠にし、通常操作から除く場合も隠さない |
| 操作回数 | アプリの開始クリック、認可署名、取引承認を別々に数える。条件変更・失敗・通信中断の追加操作を分ける |

ローカルで交換前状態を揃えて反復し、公開テストネットでは実経路と実測gasを記録する。異なる公開履歴を同一初期状態とは扱わない。
版・入力・機器・履歴量・キャッシュ・反復回数・集計方法・全試行を固定・記録し、生データから再集計できるものとする。
gasと時間を加算した単一の費用値にせず、取引内訳を取引全体と二重計上しない。
数値上限、先行方式より低いコスト、署名一回などの未測定の優位性は主張しない。

### 追試と成果の説明

第三者は自分の鍵・乱数・テスト資産と公開手順から、環境準備、正常・異常、推論と測定を再実行できるものとする。
作成者固有の非公開鍵・設定、実資金、専用の受領データ配送サービスを必須にしない。RPC等の外部依存と既知の制約を示す。
配布のためのサービスと、本体の受領データを得るための専用サービスへの依存は区別する。

サイト、CLI、コード、取引、推論記録、測定値をU-01〜U-08と対応付ける。
発表と動画で扱う内容は[既定の内容](requirements.md#発表と提出動画で扱う内容)を維持する。秒数・台本・収録は本書で定めない。
技術的なUDEL-01の証拠だけでU-03全体の達成としない。応募条件の確認と提出は[応募関連 #9](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/9)の記録と別途照合する。
動画制作・フォーム送信・応募完了や応募条件の最新調査を、本仕様書の完了条件に含めない。

| 暗号・形式証明・比較評価 | 本体設計は条件付きの基準と未証明部分を持つ。接続デモはその充足の代用にならない | FV-01〜04、EVAL、[証明義務](../../specification.md#証明義務と検証の境界) | 本体の証拠と接続の自動検証・評価を別々に追跡 |

本体の現認可に五条件の専用フィールドがないという理由だけで、本体変更を必須とは断定しない。既存の認可対象や実行文脈を用いて条件を強制できるかも、接続設計で検証する。
能力が不足すると判明した場合は「必要な能力、満たせない理由、影響する本体要件ID・仕様節、維持すべき保証、変更後の検証方法、依存の状態」を変更要求として記録する。
本体規範を変える場合は別途合意し、本体のPRD・要件・仕様・設計へ反映する。接続仕様との矛盾が未解消のまま仕様確定とはしない。
実経路の実証が残ることと、論理規則が未決・矛盾していることを区別する。

過去の文書策定IssueがClosedであることを依存解消の証拠にしない。後続担当は着手時のコード版・実行記録を確認する。
現在の作業分担では、本体の[Pool実装 #27](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/27)、[共通処理 #29](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/29)、[Ethereum接続 #30](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/30)、[結合検証 #36](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/36)と接続側の後続作業を照合する。
これらへ接続固有の交換・原子性・UI全体の責務を移さず、本体変更が必要になった部分だけ調整する。

## 後続設計と評価への引継ぎ

各パラメータは、本書で定めた意味と境界を保って設計で具体化する。方式の都合で受理条件や保証を変える場合は、上流の改訂として合意する。

| 具体化する事項 | 担当段階と決定時点 | 守る規則と境界 | 設計後に必要な検証 |
| --- | --- | --- | --- |
| Router・交換経路・銘柄・流動性 | 接続設計、接続実装前 | 全額交換、当該出力全量の帰属、中間残留なし。部分交換・返金経路は成功不可 | S-01・08〜12・18〜20を実Uniswapで実行 |
| トークン挙動・着金計測・受取先 | 接続設計、送付処理実装前 | 完了境界の`y=q≥m>0`。手数料・残高変動・再送付・既存残高での補填を除外 | 通常宛先と採用するコントラクト宛先、控除・無関係増減・異常送付 |
| 認可・暗号接続・ABI・識別・コントラクト分割 | 接続設計と必要な本体調整、実装前 | 五条件と本体出金、対象環境、意味・版の結合。表現変更での再使用不可 | 改ざん・流用・コピー・切出し・正常な別提出者 |
| 失敗伝播・再入制御 | 接続設計、資産経路実装前 | 本体から最終着金までの取消。受理した内側効果も外側失敗で取消 | 各失敗箇所と全入口の資産・成功記録比較 |
| 金額・期限の符号化と表示 | 接続設計、入力・認可実装前 | 本体の整数wei、Tの最小単位、正のm、範囲上限、`τ≤d`。不正形式・超過は拒否 | 最小値・上限・精度超過、期限前・一致・後、表示と認可の一致 |
| ウォレット・鍵構成・ブラウザ・配信 | サイト設計、サイト実装前 | 秘密鍵入力や鍵ファイル移送不要、同じウォレットで残高再利用、秘密保持 | S-31〜32、必要な本人操作と公開履歴からの復元、漏えい検査 |
| 報酬配布・資金準備・要求保存 | 配布設計、配布実装前 | 一要求一配布、額・受取先固定、自由入力、他人の要求非開示。旧試行の後成功を排除できなければ新配布不可 | S-41〜48、並行・障害・再編成、配布なし終了の根拠 |
| 見積り鮮度・自動最低額/期限・候補選択順 | 接続・UI設計、Pay実装前 | 認可開始時に`0≤age≤maxAge`、一致は有効、超過・負値・判定不能は不可。変更は再確認、認可中固定、単一入力と正の残額 | 基準時点の取得方法・時計・単位・許容幅の具体値を固定し、S-26・33〜37で幅の直前・一致・超過・判定不能と再表示を検査 |
| 確定条件・操作保持・取引照合 | 本体・接続・UI設計、同期実装前 | 採用履歴と確認時点を識別。本体と整合し、未充足は未確定、不明は確認不能 | 再編成、再読み込み、応答喪失、コピー成功、同条件再試行 |
| チェーン・ローカル環境・faucet・ホスト | 接続設計・環境担当、配布/公開前 | ローカルと公開テストネット、由来・版・初期状態。ウォレットだけの初回利用者が準備可能 | 実暗号・資産・流動性の成立、初回導線、公開URLとRPC等の前提 |
| 試験用実額・履歴・単位 | 評価計画、実行前 | `u>0`、`10u`が上限内、正の実交換出力。観測者の知識と試験秘密を分離 | 必須推論履歴と実装メタデータ、Depositとの対照 |
| 測定回数・機器・ツール・統計 | 評価計画、測定前 | 比較条件・全試行・初回/反復・成功/失敗・包含区間を固定 | 生データ再集計、第三者の追試、公開取引のgas |

上記の未選定値は方式・構成の具体化であり、五条件、全量着金、取消、要求の同一性などの意味を後から任意に変える余地ではない。
見積りの基準時点の取得方法と許容幅の具体値は採用経路に応じて定めるが、[Payの鮮度判定](#payの入力と認可開始)で定めた比較境界と認可開始の可否は変更しない。
現行本体設計の具体値・署名方式・確定設定は参照して適合を確認し、接続仕様の正本へ複製しない。

## 判断理由と仕様策定時の確認

### 合意した五つの判断

| 判断 | 採用理由と代替案との差 |
| --- | --- |
| 実行ブロック時刻で`τ≤d` | 実行可否と送信・確認の遅延を分け、観測者の時計で結果を変えない。境界一致を拒否する案との違いを明示し、一致を受理する |
| 最低受取額は正 | 支払い用途で受取下限をなくすゼロ指定を認めない。最小単位・表現範囲を検証し、黙った丸めを避ける |
| 完了時に受取人が全量保持 | 受取人を一度通過しただけの移動を着金としない。同じ処理中の転送を許す案より受取先の対応範囲は狭まるが、完了境界の資産帰属が明確になる |
| 受付済み報酬要求の内容固定 | 再送と新しい配布の意図を区別する。結果不明の要求を書き換えず、配布なしの終了後に修正した新要求とする |
| 古い認可が有効な間はUIから同入力の条件変更を開始しない | 新しい認可を作っても旧認可は失効しないため。即時の条件変更より待機が増えるが、どちらの条件が成立するか不明な競合をUIから作らない |

### 文書と数式による確認

本書作成時には、上流の規則、上記シナリオの前後状態、次の収支・識別の条件を照合した。

| 問い | 確認した根拠 | この確認だけでは示さないこと |
| --- | --- | --- |
| 正の残額とETH保存は両立するか | `0<w<V`なら`r=V-w>0`。本体債務の減少は`V-r=w`で、出金額と一致する | 実暗号の正しさ、整数符号化や実装の適合 |
| 下限と全量着金は区別できるか | `y=q≥m`を要求。`y≥m`でも`y<q`なら拒否でき、既存残高をqに数えない | トークンごとの計測方法、採用経路での帰属検証 |
| 期限境界と確定待ちは矛盾しないか | 実行の`τ≤d`と履歴の確定条件を別判定。後から期限超過しても期限内実行は有効 | チェーン・RPCの可用性、再編成が起きない保証 |
| 見積り鮮度の境界で認可開始を判断できるか | `0≤age≤maxAge`は鮮度条件を満たし、超過・負値・判定不能は認可開始不可。再表示では基準時点を更新しない | 取得経路の時計・時点の信頼性、許容幅の具体値の妥当性 |
| 再使用防止と再試行は両立するか | 成功済みpと失敗試行aを区別し、再試行前に全試行と入力を照合。失敗を成功履歴に加えない | 実経路の識別・永続化・並行処理の正しさ |
| 報酬の重複防止と追加受領は両立するか | 同一要求は一配布、受領後の明示的追加は別要求。同額を同一性の基準にしない | 配布サービスの競合制御、旧試行を終了させる方式 |
| 必須推論例に収支上の複数候補があるか | `6u+4u=10u`かつ`6u=3u+3u`、`7u+3u=10u`かつ`7u=3u+4u`。残額3uの公開後はx=6u | 同じ暗号表現の別開示、実装の全メタデータを含む秘匿 |
| 本体の取消範囲と矛盾しないか | 本体一般出金の保証を変更せず、接続が全量交換・着金までの一体取消を追加で要求する | 既存本体だけで接続を実装可能なこと |

仕様上の判断に必要な問いは上記の文書・数式・具体例で判定でき、実コードを動かさないと選べない論理規則は残していないため、仕様策定用の実験は行っていない。
認可の具体結合、取消の実経路、トークン挙動、鍵構成、実装メタデータの秘匿は設計・実装後の検証義務として残す。
これは最終成果で必須の実暗号テスト、形式証明、公開テストネット、測定・追試を任意にする判断ではない。
後続で仕様判断に追加実験が必要になった場合は、実行前に問い・影響規則・方法・判断基準を定め、入力・版・手順・結果・未検証範囲を記録する。
