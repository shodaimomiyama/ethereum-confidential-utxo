# Uniswap接続のPRD（要求定義）

- 利用する基盤: [Confidential UTXOのPRD](../../PRD.md)
- 候補比較、合意と後続作業: [Issue #9](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/9)
- 公開デモサイトとUIの要求の具体化: [Issue #16](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/16)

## 目的

機密ETHで報酬を受け取った個人が、その一部をUniswapの公開流動性で交換して相手の希望するトークンで支払い、残りを機密UTXOとして使い続けられるようにする。
取引グラフと支払額の公開を許容する用途で、金額の機密性と利用コストの両立を目指すConfidential UTXOを活用する。

このPRDは、接続によって追加する利用価値と成功条件を定義する。
本体の機能、暗号、安全性、比較評価と標準化の要求は、[本体のPRD](../../PRD.md)で管理する。
低コストは本体の設計上の狙いであり、先行方式に対する優位性は比較結果で裏付けられた範囲で述べる。

## 背景と課題

機密ETHを受領できても、相手が公開トークンでの受取りを求める場合には、出金と交換が必要になる。
利用者が途中で公開ETHを受け取り直す手間や、交換失敗後に出金だけが残る状態への対処を避け、支払いと残額の継続利用を完結できるようにする。
支払額の公開を受け入れる場合にも、過去の報酬額や未使用の残額について、どの条件なら機密性が残るかを確認する必要がある。

[RAILGUNのCross-Contract Calls](https://docs.railgun.org/developer-guide/wallet/transactions/cross-contract-calls)には、機密残高からの出金、外部交換、再秘匿を組み合わせ、失敗時に取り消す先行例がある。
本プロジェクトは、公開グラフ型の本体から支払いを完結する選択肢を追加し、その実際のコストと機密性の限界を示す。
同様の支払いが既存手段では不可能だとは主張しない。
利用者需要と、限定した機密性に見合う費用上の利益は検証する仮説として扱う。

## 対象者と利用シナリオ

主な利用者は、Confidential UTXOでETHの報酬を受け取り、その一部を店舗やサービスなどへの公開トークンの支払いに使いたい個人である。
支払い先が最低受取額を超える受取りを許容する場面を対象とする。
請求額と厳密に一致する決済や、一般利用者向けの完成した決済サービスは今回の対象外とする。

主な利用シナリオは次のとおり。

1. 利用者が報酬を機密ETHで受領し、金額を確認して使用できる状態にする。
2. 使用するETH額、交換先トークン、最低受取額、最終受取人を指定して支払いを認可する。
3. 認可した固定額のETHを全額Uniswapで交換する。最低受取額以上が届く場合に支払いを成立させ、交換で得たトークンの全量を最終受取人へ渡す。
4. 支払いに使わなかったETHは利用者の機密UTXOに残り、利用者がその残額を再送金できる。
5. 交換や着金条件が成立しない場合は支払いの資産操作を取り消し、当該試行による入力UTXOの消費を残さない。再試行の扱いは、[本体仕様の操作の再使用と競合](../../specification.md#操作の再使用と競合)に従う。

事業者の経費支払いや、自分が使用する公開トークンへの交換も同じ機能の応用となる。
組織の承認や会計の機能は追加しない。
開発者と評価者には、この経路の実装、公開情報、費用と失敗時の結果を追試できる成果を提供する。

### 支払いに関わる用語

本体の所有者と提出者の定義は、[本体の要件定義](../../requirements.md)に従う。
接続では、出金先と支払い先を区別するために次の語を使う。

| 用語 | 意味 |
| --- | --- |
| 支払者 | 使用するUTXOの所有者として支払いを認可する利用者 |
| 最終受取人 | 交換後の公開トークンを受け取る相手。本体からETHを受け取る公開出金先とは区別する |
| 最低受取額 | 支払いを成立させるために最終受取人へ届く必要があるトークン額の下限。厳密な請求額ではない |
| 残額 | 今回の固定ETH使用額を差し引いた、本体に保持するUTXOの金額。交換後の余剰ETHの返還を指すものではない |

## 要求と成功の判断

| 要求ID | 要求 | 成功の判断 |
| --- | --- | --- |
| U-01 | 機密ETHの一部を相手の希望する公開トークンで支払い、残額を使い続けられる | 報酬の受領、固定ETH額の交換、指定した最終受取人への最低額以上の全量着金、残額UTXOの再送金が一連の利用として成立する |
| U-02 | 支払い失敗後の途中状態への対処を求められない | 交換または着金条件の不成立時に、支払いに伴うUTXOの消費と生成、出金、交換と着金の資産効果を一体に取り消し、出金だけを残さない |
| U-03 | 応募用PoCで接続の追加価値を示す | 公開デモサイトで実暗号の検証と資産移動を伴う操作を示し、正常動作と重要な失敗時の結果をCLIでも追試でき、応募条件を満たす |
| U-04 | 利用者が認可した支払条件が守られる | 使用ETH額、交換先トークン、最低受取額と最終受取人を第三者が変更して支払いを成立させられない |
| U-05 | 支払い後に残る機密性と限界を判断できる | 公開情報のみから報酬額と残額が一意に決まらない利用例と、既知額や後続操作によって判明する対照例を、観測者の知識とともに再現できる |
| U-06 | 支払いに必要なコストを判断できる | 実暗号を伴う支払いの実行コストと証明生成時間、および通常の公開交換に対する追加負担を、条件とともに測定できる |
| U-07 | 第三者が経路と主張を検証できる | CLIと再現スクリプトで、正常動作、取消、認可した条件の保護、機密性の例とコスト測定を追試できる |
| U-08 | 初回訪問者が公開サイトから支払いを体験できる | Ethereumウォレットを持つがテストETHと機密残高を持たない人が、サイトの案内からテストETHの取得、鍵の初期設定、入金またはデモ報酬の受領、支払い、残額の公開ETHへの出金まで進める。デモ報酬を用意した理由と機密性の限界を理解できる |

U-01は従来の公開トークン受取りを、報酬の受領から残額の再利用までの支払い用途へ具体化した。
U-02は従来の出金と交換の取消を維持し、着金条件まで対象を明確にした。
U-03は応募条件の充足を維持し、応募先をFrom Scratchへ変更して、応募用PoCで示す証拠を明確にした。
U-04〜U-07は、意図の保護と、従来は成果の候補だった評価と追試を必須成果として追加した。

U-02では同一トランザクションへの包含だけを成功の証拠にしない。
必要な失敗伝播と取消範囲を接続側で定め、検証する。
外側のgas支出は取消の対象に含めない。
支払いの具体的な受入条件は後続の要件定義と仕様で定める。

## 公開情報と機密性の限界

公開交換では、使用ETH額、交換後のトークンと金額、最終受取人が公開される。
本体の取引グラフも公開され、所有者情報や外側のトランザクション送信元の秘匿は保証しない。
公開範囲の前提は、[本体仕様の公開情報と秘密の範囲](../../specification.md#公開情報と秘密の範囲)に従う。

U-05の主な観測者は、公開チェーン情報を得られるが、利用者の秘密鍵や報酬額などの非公開情報を持たない第三者とする。
報酬の支払元は元の報酬額を知り、最終受取人は自分が受け取った額を知る。
これらの相手の知識や、相手間の情報共有によって追加の推論ができる場合も説明する。
取りまとめ役への秘密の開示を、今回の必須経路の前提には置かない。

残額を機密UTXOとして使えることは、その金額が推論されないことを保証しない。
入力額が既知なら公開出金額との差から残額が分かり、後続の全額出金から過去の報酬額が判明する場合もある。
機密性が残る例では、公開グラフ、入出金、所有者に関する情報と実装のメタデータを含めて評価する。
収支だけから得た候補額の幅と、採用する暗号方式が提供する秘匿の根拠を区別する。
公開された金額や履歴を後から消すことは保証しない。

## 今回の範囲と対象外

実資金を扱わない研究用PoCとして、ETH専用の本体と、一種類の公開トークンへ交換する接続を提供する。
交換先はデモで扱う一銘柄に絞り、銘柄と実行環境は後続で選定する。
成果の提供形態は、公開URLでアクセスできるプロダクトのデモサイト、CLIと再現スクリプトとする。
サイトは紹介ページとアプリ画面で構成する。紹介ページで利用価値、仕組み、公開情報と機密性の限界を説明し、アプリと検証結果・コードへ案内する。
紹介ページとアプリの表示言語は英語とする。
対面発表ではサイトを直接操作し、提出動画は同じ説明・操作の流れを事前収録する。収録動画は対面発表の予備としても用意する。
扱う内容は今回定め、秒数配分・収録・編集は[動画制作 #20](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/20)で決定する。
ホスト先は未選定とし、Vercel等の特定サービスの採用や、サイトの公開が公式応募条件であることは本書で確定しない。

### 初回利用者の体験

利用者はEthereumウォレットを持っていることだけを開始条件とし、テストETHや機密残高を事前に持つこと、運営者に個別の準備を依頼することを求めない。
対応ネットワークへの切替、テストETHの取得、機密資産用の鍵の初期設定をサイトから案内する。
テストETHは外部faucetへの案内で取得する。サイト独自の公開ETH配布機能は必須にしない。
入金用ETHと、その後の支払い・出金に必要な公開ETHのgasを区別する。
同じウォレットで再訪した場合は、別ブラウザでも以前の機密残高を再利用できることを求める。具体的な鍵の構成は設計で実証する。
アプリの主導線は「デモ報酬を受け取って支払う」とし、Depositは別の選択肢として案内する。
中央カードを「Demo reward / Pay / Deposit / Withdraw」で切り替え、初回はDemo rewardへ案内する。ウォレット、ネットワーク、公開ETHと機密UTXOの残高を共通表示する。
進行中の操作と直近の結果はタブを切り替えても確認できるようにする。全履歴の一覧画面は「Coming soon」とし、残高の再同期は提供する。

同じサイトで次の機能を提供する。

| 機能 | 利用者ができること |
| --- | --- |
| Deposit | 公開ETHを自分のUTXOへ入金し、確定後に利用可能額を確認する |
| デモ報酬の受領 | デモ用の支払元から機密ETHを実際に受領し、その一部を公開トークンの支払いに使う |
| 支払い | 固定ETH額を全額交換し、指定した最終受取人へ出力トークン全量を届ける |
| 残高と処理結果 | 公開ETHと機密UTXOの残高を区別し、再同期、処理状態の確認、Explorerでの確認を行う |
| Withdraw | 選んだUTXOの全額を自分のウォレットへ公開ETHとして戻す。複数UTXOがある場合は対象と金額を確認できる。公開出金が過去の金額推論につながることを確認する |

支払いでは、指定額を賄えて正の残額が残る単一UTXOをアプリが自動選択し、詳細で選択結果を確認できるようにする。
単一UTXOで支払えない場合は、合計残高だけで実行可能と表示しない。複数UTXOをまとめる支払いUIは「Coming soon」とする。
見積り更新で認可条件が変わる場合は、変更内容を表示して再確認を求め、認可開始後に条件を変更しない。
支払額、宛先、デモ報酬額の初期値は空欄とする。宛先には自分のアドレスを使う操作を設け、相手のアドレスを事前に用意しなくても試せるようにする。
入金、デモ報酬、支払い、出金の各取引は、取引ハッシュが取得でき次第、対応するExplorerの取引ページへ直接移動できるようにする。

ウォレット自体の作成、入金から交換・支払いまでを一つの資産操作にする機能、汎用的な機密送金UIは必須にしない。
残額の機密再送金UIと動画での操作実演は対象外だが、残額再送金と受領の既存検証は維持する。
部分出金UIも今回の対象外とする。本体の部分出金機能と検証は維持する。
対象外機能を画面に置く場合は「Coming soon」と明示して実行できない状態にし、今回提供する機能と区別する。表示することを実装完了や提供日の確約として扱わない。

### デモ報酬を用意する理由

Depositは、初回利用者が自分の資産を入れて操作を試す入口となる。
ただし、公開額を単一UTXOへ入金し、そのUTXOから直ちに一部を公開支払いした場合、公開入金額と支払額の差から残額が判明する。
この経路だけでは、報酬額と残額に複数の候補が残る利用場面を体験できない。

そこで、デモ用の支払元が機密送金する報酬を受け取り、そこから支払う入口も用意する。
公開情報だけでは報酬額と残額に複数の候補が残る履歴を用い、本人が確認できる金額と公開情報の違いを説明する。
この理由を紹介ページとデモ報酬の入口に記載する。単に表示を隠す機能や、入金すれば必ず金額が分からなくなる仕組みとして説明しない。

報酬の支払元は配布した実額を知る。支払元に対して報酬額や残額が秘匿されるとは主張しない。
デモ報酬の金額は利用者が自由に入力する。固定額やデモ専用の入力範囲を設けず、正の金額、本体の金額上限、配布元の利用可能資金の範囲で受け付ける。
実行できない場合は理由と金額の修正方法を表示する。無制限の配布を保証するものではない。
連打や通信中断後の再読み込みは同じ受取要求として確認を継続し、一つの要求から二重に配布しない。結果が不明な間は元の要求を確認する。
受領完了後に利用者が明示的に始める追加要求は認める。同じ要求の重複防止を理由に、1人1回や日次の配布上限は導入しない。
公開の固定配布額、API応答、ログ、配布規則などが実額を明らかにする場合、その情報を除外して機密性を主張しない。
自由入力で作られたすべての履歴に機密性が残るとは保証しない。複数候補が残るデモの履歴と、既知額などから判明する条件を区別する。
配布機能の具体的な方式・運営条件と、成立する機密性の評価は、要件の具体化と後続設計で定める。

### 維持するデモと検証

発表と提出動画では、紹介とデモ報酬の理由、報酬受領から支払い・残額確認・Explorerへの遷移、最低受取額未達による取消、機密性と限界、実測コストと証拠への導線を扱う。
faucet、Deposit、Withdrawは動画では入口の紹介に留め、各機能の実行検証は維持する。
本人画面の試験用実額は収録してよいが、視聴者が実額を知ることと、公開チェーン情報のみを持つ観測者に対する機密性評価を区別して説明する。鍵や秘匿用乱数は収録しない。

必須のデモと証拠は次のとおり。

| 対象 | 示す内容 |
| --- | --- |
| 正常な利用 | 実暗号を用いる報酬の受領、Uniswapでの交換と最低額以上の着金、残額の再送金 |
| 失敗と意図の保護 | 最低受取額を満たさない場合や交換処理の失敗による資産効果の取消。支払条件の改ざんが成立しないこと |
| 機密性 | 支払い後も報酬額と残額が一意に決まらない例と、既知額や後続操作から判明する例 |
| コストと追試 | 実行コストと証明生成時間、公開交換との差、公開情報、使用した版と実行手順 |

通常の公開交換との比較は、同じ交換条件と環境で、機密資産からの支払いに追加される負担を説明するために行う。
報酬の受領から残額の再送金までの各操作と、支払い単体の費用を区別する。
比較対象に含める操作、証明生成や同期などの計測範囲は後続の要件定義で定める。
先行機密方式より安いことの実証は応募用PoCの必須条件に含めず、[本体の比較評価要件](../../requirements.md)は引き続き維持する。

任意の成果は、同条件で追加できる先行機密方式との比較や、同じ機能を使った別の支払い例とする。
上記以外の汎用ウォレットGUI、請求額ぴったりの決済、交換額の秘匿、交換後のトークンの再秘匿、本体の多資産化、複数人の集約交換、ENS連携、組織の承認と会計、本番運用は対象外とする。

## 本体との責務と未対応の依存条件

本体は、仕様としてコントラクトへのETH出金、部分出金後の残額の保持、所有者の認可と論理操作単位の取消を定めている。
これらが実装済みであることは、このPRDの前提にしない。

| 本体の既定の振る舞い | 接続側で成立させる事項 |
| --- | --- |
| [基本操作](../../specification.md#基本操作)で定めるETHの入金、送金と部分出金 | 固定ETH使用額を交換し、最低額以上の全量着金と残額の再利用を示す |
| [認可対象](../../specification.md#認可対象)に含まれる公開出金額と公開出金先 | 出金の認可と、交換先トークン、最低受取額、最終受取人を結び付け、別の支払いへの流用を防ぐ |
| [複数操作と外部接続](../../specification.md#複数操作と外部接続)で区別する本体の取消範囲 | 出金から交換と着金までの失敗伝播と取消を検証する |
| [受領の保証](../../specification.md#受領の保証と不整合な受領データ) | デモで受け取った報酬と、支払い後の残額を本人が確認して再使用できることを示す |

本体の公開出金先はETHを受け取る接続コントラクトになり得るため、最終受取人とは区別する。
認可済みの内容を提出する者に、支払条件を変更する権限を与えない。

現時点で本体への機能変更は採用していない。
固定額の部分出金は既存仕様に対応するが、交換固有の条件と出金認可を結び付ける実経路は未実証である。
後続で本体の認可対象や操作の変更が必要と分かった場合は、[Issue #9](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/9)に変更理由、影響する要件と仕様節、維持する保証、確認方法を記録する。
その変更を未対応の依存条件として扱い、本体側の要求、要件、仕様と設計を整合させてから実装する。

## 制約と開発の区切り

| 項目 | 制約 |
| --- | --- |
| 基盤との関係 | ETHを対象とする公開グラフ型Confidential UTXOを利用する。本体と接続の要求、要件、仕様と設計を分ける |
| 応募対象 | ETHGlobal Tokyo 2026のClassic（From Scratch）で参加し、Uniswap Foundation「Best Uniswap Stack Contribution」の通常枠を対象とする |
| 優先順位 | 応募資格を最優先とし、その条件下で利用者への価値、実際に動く最小経路、保証と証拠の一致を優先する |
| 本体の完成との関係 | 応募用PoCは本体全体の比較評価や形式証明の完了に先行してよい。本体の未完了要件を免除しない |
| 公開サイトの追加 | 初回利用者向けUIとデモ報酬の提供を含める。CLI、両環境の実暗号検証、機密性・コスト評価、残額の再送金検証は維持する |

2026年9月26日に確認した[公式提出案内](https://ethglobal.com/events/tokyo2026/info/details)では、提出締切は2026年9月27日09:00 JSTである。
正式な参加資格、提出物と手続きの確認状況は[Issue #9](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/9)で管理し、[公式賞金ページ](https://ethglobal.com/events/tokyo2026/prizes/uniswap-foundation)の条件と照合する。
受賞は外部評価であり、技術的仮説の成立や安全性の証明にはしない。

## 将来像と成果の使い方

Ethereumアプリケーションが、用途に必要な機密性と費用を選び、既存の公開流動性を使えるようにする。
今回の支払いを、その条件を判断できる最初の利用例とする。
接続コード、失敗時の結果、機密性とコストの評価、追試手順を再利用できる形で提供する。
SDK化、別の接続例や他の機密台帳への適用は、今回の結果を踏まえて検討する。

## 後続で具体化する事項とリスク

| 段階 | 引き継ぐ判断と成果 | 完了を判断する条件 |
| --- | --- | --- |
| 接続の要件定義 | U-01〜U-08の検証可能な受入条件、初回利用の導線、コスト比較の範囲、機密性評価の観測者と入力条件 | 正常時と重要な失敗時に必要な証拠が要求ごとに対応する |
| 接続の仕様 | 支払いの認可対象、入力と結果、最低受取額の意味、取消範囲と公開情報 | 受理と拒否、資産の帰属、本体との責務が方式に依存せず定まる |
| 設計と必要な実験 | 本体の実経路への接続、Uniswapの利用箇所、流動性、証明生成と認可の構成 | 採用構成が仕様を満たす根拠があり、未実証の依存と必要な本体変更が明らかになる |
| 実装と検証 | CLI、実暗号、資産移動、取消、改ざん拒否、機密性とコストの追試 | 最小デモと証拠を第三者が再現でき、未完了の本体要件を区別できる |
| 公開サイトと初回利用 | 紹介ページ、入金・報酬受領・支払い・出金、テストETHの取得導線、鍵の初期設定、再同期 | 運営者による個別準備なしに初回利用でき、デモ報酬の目的と公開範囲を説明できる。配布・鍵・ホストの具体構成は未選定 |
| 応募準備 | 参加資格、必要な提出物とAI利用の説明 | 公式条件の充足を確認できる |

Routerの版、交換経路、ネットワーク、銘柄、認可形式、暗号方式とコントラクトの分割は未選定とする。
本体の[設計と必要な実験 #7](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/7)および[環境構築 #4](https://github.com/shodaimomiyama/ethereum-confidential-utxo/issues/4)と、接続が必要とする実装と実行環境を照合する。
実現性、機密性や費用の確認結果から要求を変更する場合は、このPRDへ反映する。
