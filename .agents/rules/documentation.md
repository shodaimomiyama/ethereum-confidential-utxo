# リポジトリの文書管理ルール

文書の作成、更新、移動、削除と、調査結果をリポジトリへ保存する際に適用する。
以下のパスはリポジトリルートを基準とする。

## 規則の管理

- ルートの `AGENTS.md` は実ファイルとして管理し、エージェント運用、ドキュメント索引、規約への案内を記載する。
- 詳細な規約の正本は `.agents/rules/` に置き、`AGENTS.md` からMarkdownリンクで参照する。規約の内容は入口に複製しない。
- 規約を追加する際は、`AGENTS.md` に参照先と読む条件を記載する。
- 変更後は文書索引と規約への参照が解決できることを確認する。

## Markdownファイルの新規作成

- 新しい `.md` ファイルを作成する前に、予定するパスと目的を示し、ユーザーの明示的な承認を得る。
- 現在の依頼で対象ファイルまたは作成範囲が明示的に許可されている場合は、その承認範囲で進める。承認済みの作成について再確認は求めない。
- 整理の都合や補助資料の必要性だけで作成範囲を広げない。承認されていない追加文書が必要になった場合は、作成前に確認する。
- 既存文書の編集やユーザーが指示した移動は、その依頼の範囲で行う。移動に合わせて別の文書を追加する場合は、新規作成として扱う。

## 文書の役割

| 文書 | 答える問い | 記載する内容 |
| --- | --- | --- |
| PRD（要求定義） | 誰の、どんな課題を、なぜ解決するか | 背景、対象者、提供価値、利用シナリオ、目指す成果、対象範囲と対象外、優先順位、制約 |
| 要件定義 | 要求を満たすために、何が成立していなければならないか | 機能、機密性と安全性の保証、性能と運用条件、検証可能な受入条件 |
| 仕様書 | どの振る舞いを、正しい実装として認めるか | 状態遷移、入出力、データ形式、インターフェース、検証規則、異常時の振る舞い。暗号プロトコルの数式、証明対象、符号化も含む |
| Design doc | その仕様を、どの構成で実現し、なぜその設計を選ぶか | コンポーネントの責務、依存関係、処理の構成、採用技術、代替案、トレードオフ、実装上のリスク |

仕様書は実装が従う規則、Design docはその実現方法と選択理由の正本とする。
例えば、暗号方式の採用理由と比較はDesign docへ、実装間で一致すべき検証式や符号化は仕様書へ置く。

PRDには成果の成功指標と重要な制約も記載する。
「第三者がコストと機密性の限界を評価できる」は要求であり、測定条件や合格条件は要件定義で具体化する。
既に合意した前提は制約として記載し、具体的な実現方法と混同しない。

指定された作業段階に合わせて文書を作成する。
要求定義だけの作業で、要件定義、仕様書、Design doc、実装を先回りして追加しない。
実現性の調査で要求の成立に関わる問題が見つかった場合は、根拠を示して要求と制約を見直す。

## 配置と責務の分離

- Confidential UTXO本体のPRD、要件定義、仕様書、Design docは `docs/` 直下に置く。本体のPRDは `docs/PRD.md` とする。
- 外部接続の文書は `docs/integration/` 配下に接続先ごとに置く。Uniswap接続のPRDは `docs/integration/uniswap/PRD.md` とする。
- 本体と接続はそれぞれ提供価値と成功条件を持つ。本体の操作と保証は本体側、接続固有の条件と組合せの保証は接続側で定義する。
- 接続側は本体の文書を参照し、仕様を複製しない。不足する機能は本体への変更要求として明示する。
- 合意済みの内容、提案、後続で具体化する事項を区別する。設計で要求や要件を変更する必要が生じた場合は、上流の文書へ変更を反映する。

## 調査資料の保存基準

`docs/research/` には、特定のイベントや作業が終わった後も、このリポジトリの理解、設計判断、実装、検証に利用する技術的な資料を置く。
保存前に、その資料を何の判断や検証に再利用するかを明確にする。
この保存基準を満たしても、新しいMarkdownファイルの作成には上記の承認が必要となる。

| 保存する内容 | 保存対象外の内容 |
| --- | --- |
| 暗号方式や先行実装の比較、保証と制約、採用判断の根拠 | ハッカソンの開催日、賞金、応募条件、賞を選ぶための比較 |
| 再現可能な測定方法と結果、失敗条件、実装上の知見 | 当日の予定、個人の稼働時間、日々の進捗、提出の準備メモ |

- 技術的な知見と一過性の情報が混在する場合は、長期的に利用する知見を抽出する。一過性の文書を別ディレクトリへ移すだけで残さない。
- 一過性の作業情報は会話やIssueなどの作業管理先で扱う。要求に直接影響する期限や制約は該当PRDに必要な範囲で記載し、イベント情報全体を複製しない。
- 技術資料には根拠となる一次資料、対象の版や確認時点、未検証の範囲を示す。古くなる可能性のある技術情報は、適用条件を明記して残す。
- 調査結果、提案、合意済みの要求を区別する。調査文書だけで要求、要件、仕様を確定しない。

## 変更時の確認

文書の移動、削除、見出し変更では、参照元と案内を更新する。
完了前に、変更前のパスへの参照が残っていないことと、ローカルリンクと見出しリンクが解決できることを確認する。
